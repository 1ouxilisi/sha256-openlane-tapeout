# 架构说明：SHA-256 加速器 RTL

这份文档讲的是**电路怎么做的**，不是指标多好看。README 讲成果，VERIFICATION 讲证据，这里讲设计本身——包括哪里偷了懒、哪里是被面积逼出来的选择。

对应源码：

| 文件 | 行数 | 作用 |
|---|---|---|
| `designs/sha256/src/sha256_top.v` | 111 | 顶层封装：32-bit 串行接口 + 消息装载 / 摘要读出状态机 |
| `designs/sha256/src/sha256_pipe.v` | 271 | 压缩核：64 轮、三级流水、K 常量与逻辑函数内联 |

---

## 1. 设计边界

先说清楚不做什么，省得读到后面以为漏了：

- **只算单块**：输入 512-bit 消息块 + 内部 IV，输出 256-bit 摘要。**padding 不在硬件里做**——`0x8000…` 和长度域由 testbench / 上位机填好再送进来。
- **不做多块流式**：一块算完把 `done` 拉高、摘要倒出来，再装下一块。多块串联（Merkle-Damgård 链）需要上位机把上一块的 `digest` 当下一块的 IV 送回来。
- **没有 AXI/APB**：太占 IO，也用不上。手写握手足够。
- 无 DFT 扫链、无时钟门控、无 ECO 补丁（见第 7 节）。

---

## 2. 顶层接口与握手

71 根 IO（v1 那版并行接口是 773 根，die 面积一半以上被 pad 吃掉；改成串行是 v2 的核心动作）。

| 信号 | 方向 | 位宽 | 含义 |
|---|---|---|---|
| `clk` / `reset_n` | in | 1 | 同步时钟、异步复位低有效 |
| `wen` | in | 1 | 写消息字使能 |
| `wdata` | in | 32 | 消息字（big-endian 字序） |
| `start` | in | 1 | 启动压缩（需 `msg_full` 已置位） |
| `busy` | out | 1 | 压缩中，期间忽略 `wen` |
| `done` | out | 1 | 压缩完成，摘要已锁存 |
| `rvalid` | out | 1 | 摘要字读有效 |
| `rdata` | out | 32 | 摘要字输出（big-endian，先读最高字） |

一块数据的完整时序：

```
        __    _16 拍写满_       __             __  _8 拍读_    __
wen   __|  |__________________|  |___________|  |__________|  |_____
       M0 M1 ... M15           |              |
start ______________________|__|              |______________________
busy  _____________________|       64 轮 × 3 拍        |____________
done  ______________________________________________|__|__________|___
rvalid ____________________________________________|  D0..D7   |______
rdata  ____________________________________________|  D0..D7   |______
```

- 写指针 `wptr` 0→15，`msg_reg[(15-wptr)*32 +: 32] <= wdata`，所以**第 1 拍写的是 M[0]**（最高 32 位）。
- 16 拍写满才置 `msg_full`；`start` 必须等 `msg_full`，否则被忽略。
- `core_done` 来的那一拍：`busy` 落、`done` 起、`digest` 锁存、`rptr` 归零。
- 之后连续 8 拍输出 `digest[(7-rptr)*32 +: 32]`，第 8 拍（`rptr==7`）同时清 `rvalid` / `done` / `reading`，回到可写入状态。
- `busy` 和 `reading` 期间都禁写，防止压缩中途把 `msg_reg` 覆盖掉。

## 3. 压缩核的三级流水

`sha256_pipe` 有四个状态：`IDLE → COMPUTE → ACCUM → FINISH`。真正吃时间的是 `COMPUTE`：**64 轮，每轮固定 3 个时钟**。

| 拍 | 干什么 | 组合深度 |
|---|---|---|
| phase 0 | 算本轮消息字 `wc`：`t<16` 直接取输入字；`t>=16` 用 16 字窗口扩展 `σ1(W[t-2]) + W[t-7] + σ0(W[t-15]) + W[t-16]` | 3 个 32-bit 加法 + 两次旋转异或 |
| phase 1 | 并行算 `t1p = H + Σ1(E) + Ch(E,F,G) + K[t]` 与 `t2p = Σ0(A) + Maj(A,B,C)` | 一条 4 项加法链，两条链互相独立 |
| phase 2 | 收尾：`E <= D + t1p + wc`、`A <= (t1p + wc) + t2p`，同时 `H←G←F←E`、`D←C←B←A` 移位，`W[t[3:0]] <= wc` | 2 次加法 + 寄存器更新 |

关键在 phase 1 的切法：SHA-256 单轮本来是

```
t1 = H + Σ1(E) + Ch(E,F,G) + K[t] + W[t]
t2 = Σ0(A) + Maj(A,B,C)
E' = D + t1
A' = t1 + t2
```

如果一级算完 `t1` 再算 `A'`，就是一条 4→5 项的加法长链。拆成 `t1p`（去掉 `W`）和 `t2p` 之后，phase 1 里两条链各自并行，`wc` 在 phase 0 已经躺好了；到 phase 2 只剩下 `t1p + wc` 和 `+ t2p` 两次加法。**代价是每轮多一拍（3 拍而不是 2 拍），收益是每条组合链短了将近一半**——这就是 v2（两级、53.45 MHz）到 v3（三级、58.17 MHz）的全部内容，没有改算法。

## 4. 消息窗口 `W[0:15]`：面积的主因

`W` 是一个 16×32 的寄存器数组，滚动复用的环形窗口：

```verilog
assign w_cur = (t < 16) ? msg[(15 - t)*32 +: 32]
                        : (sigma1(W[(t-2)%16]) + W[(t-7)%16]
                           + sigma0(W[(t-15)%16]) + W[(t-16)%16]);
```

写完 64 轮后，`W[t[3:0]] <= wc` 把当轮的字写回窗口，供后面 15 轮引用。

这个写法简单、正确、只用一个 512-bit 数组，但**在硬件里 `(t-k)%16` 是动态索引**——综合后每个索引变成一棵 16 选 1 的 mux 树。四个索引 × 32 bit ≈ 1,920 个 `mux2`，这也是综合结果里 `mux2_2` 高达 **2,239** 个的直接原因（占 18.2%）。

> 已知的改进方向（**未做、未验证**）：把 `W` 改成 16 级移位寄存器链，每拍整体右移一格，索引就退化成固定连线，mux 能省掉一大半。代价是写口变复杂、每拍 512 bit 全部翻转（动态功耗上升）。按 v6 的功耗结构（时钟树 49.1% + 触发器 48.1%，组合逻辑只有 2.8%），省 mux 对总功耗的帮助可能不如预期，所以没有动。

## 5. 面积与单元构成（来自 v6 综合结果）

| 项 | 数量 | 占比 |
|---|---|---|
| 触发器 `dfrtp_2` + `dfstp_2` | 1,945 + 2 = **1,947** | 15.8% |
| 缓冲 `buf_1` | **2,532** | 20.6% |
| 二选一 `mux2_2` | **2,239** | 18.2% |
| 其余组合门（a22o/a221o/o21a/nand/nor/xor…） | 约 3,562 | 29.0% |
| **合计** | **12,288** | 100% |

触发器数量能对上账：`msg_reg` 512 + `W` 512 + `A–H` 256 + `digest` 256 + `wc/t1p/t2p` 96 + 指针与控制位约 50 ≈ 1,660 bit，加上综合时引入的额外寄存，落在 1,947 是合理的。die 面积 0.4096 mm²、利用率 45.18%，即标准单元区约 0.185 mm²。

`buf_1` 那 2,532 个不是设计写的，是综合/布线阶段为了驱动扇出和修 hold 插的。把它们剔掉之后净逻辑约 9,756 个单元——这也解释了为什么用裸 yosys 独立综合只有 9,248 个（差 5%）。

## 6. 频率到底是几个

这一节容易误会，写细一点：

- `metrics.csv` 里 v6 的 `critical_path_ns = 8.2`，那是 **OpenROAD 布线后的内部估算**，不是签核值。它看起来"8.2 ns 够跑 120 MHz"，但内部估算用的是简化寄生模型。
- 真正的判据是 **SPEF 寄生提取 + 三 PVT corner STA**：v6 在最紧角（`rcx_max`）setup 余量 **+1.25 ns @ 24 ns**，因此真实上限约 **22.75 ns ≈ 43.9 MHz**，再压就进负余量区。
- 换句话：三级流水把每轮压到 3 拍、每拍组合约 8 ns 量级，这是**结构性收益**；但 die 上真实的互连延迟、时钟树偏斜、corner 差异，把可达频率从"数据路径允许的 100+ MHz"拉回到 41.67 MHz。**约束应该跟着工艺能力走，不是跟着愿望走**——这是 v5 的全部结论。

---

## 7. 为什么不再加深流水

从两级到三级，频率 53.45 → 58.17 MHz（+8.8%，签名前的 resizer 估算口径），但代价是每轮多一拍 + 多一层流水寄存器。再往下拆有两个问题：

1. **收益递减**：每轮已经 3 拍，再拆到 4 拍，每拍组合只短一点点，但总周期数从 192 拍涨到 256 拍（+33% 延迟），吞吐直接掉三分之一。
2. **寄存器成本**：多一级流水 = 32-bit × 若干中间变量的寄存器墙，die 已经收到 640×640、利用率 45%，加寄存器就要加面积或降利用率。

对单块哈希这种"延迟敏感、吞吐不敏感"的用法，3 拍/轮是甜点。如果要做多块流式的吞吐型设计，正确方向不是加深流水，而是**多路并行 + 轮内展开**（例如 2 路交织共用同一套 K 常量），那个工程量远大于本项目。

## 8. 已知限制（诚实清单）

| 限制 | 影响 | 为什么没做 |
|---|---|---|
| 无硬件 padding | 输入必须已补好位 | padding 需要长度域与分支，属于接口层职责 |
| 无多块流式 | 每块要重新握手 | 需要 IV 回送通路，增加 IO 与控制复杂度 |
| 无 DFT 扫链 | 不可测 | 超出零成本开源流片的范围，不做假声明 |
| 无时钟门控 | 空闲也在耗时钟功耗 | sky130 下门控单元与流程支持有限 |
| `W` 用动态索引 | mux 占 18.2% 面积 | 移位寄存器方案功耗收益不确定，未验证 |
| v1–v4 签核不合格 | 那四代的 GDS 只能当过程产物 | 约束偏离工艺能力，v5 才修正 |

```bash
python3 scripts/check_vectors.py  # 用 hashlib 独立核对期望值

```

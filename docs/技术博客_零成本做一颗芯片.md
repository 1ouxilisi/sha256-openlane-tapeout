# 零成本做一颗芯片：我用 OpenLane 把 SHA-256 从 Verilog 做到了 GDS

> 商用 EDA 一年几十万，流片一次上百万。但芯片设计的"完整闭环"，其实可以在零成本下跑通。我用 OpenLane + SkyWater 130nm，把一颗 SHA-256 加速器从 RTL 做到真实 GDS 版图，七代迭代，从"能出 GDS"走到"时序签核、LVS 与 DRC/密度都落在同一版上"，再把余量边界量出来：v4 做到 56.72 MHz、0.41 mm²、40.65% 利用率、0 布线违例；v5 把约束改对，26 ns 下三 PVT corner 全部 WNS = 0；v6 加压到 24 ns（41.67 MHz），三 corner 仍全部为正；v7 换调度结构，同 die 提到 **55.56 MHz**，并在同一版上把 LVS、KLayout DRC 与金属密度一次跑完。

---

## 一、为什么做这件事

先说清楚：这不是要造一颗能卖的芯片。SHA-256 加速器在商业世界里毫无稀缺性，58 MHz 放在 7nm 时代更是慢得可笑。

我想验证的是另一个问题：**一个没有流片预算、没有商业 EDA 授权的人，能不能把芯片设计"从 Verilog 到 GDS"这条完整链路真正走一遍？** 不是画个框图，不是跑个仿真，而是产出可打开的版图文件、可核对的时序报告、可复现的物理实现。

答案是可以，而且成本为零——前提是接受一个工艺：SkyWater 130nm。它是目前唯一完全开源、可零成本产出真实 GDSII 的 PDK，配合 OpenLane 1.1.1 全流程（Yosys 综合、OpenROAD 布局布线、TritonRoute 详细布线、Magic/KLayout 物理验证），足以跑通一个中等规模数字设计的全部环节。

选 SHA-256 也是刻意的：它运算路径长、适合体现流水线价值；算法固定、输出可由 Python `hashlib` 逐位核对，正确性有绝对标准，不会"跑通了但不知道对不对"。

## 二、七代迭代：每一代解决一个真问题

### v1：先跑通，哪怕很丑

第一版是最朴素的：单块组合逻辑实现压缩核，773 个并行 IO，不做任何流水线。目标只有一个——确认整条链路能出 GDS。

结果：**38.58 MHz、0.64 mm²、利用率 20.99%、0 布线违例**。

三个短板暴露得很清楚：
1. 频率只有 38.6 MHz，根因是没有流水线，压缩核的超长组合路径直接落在关键路径上，SPEF 静态时序 WNS 达 **-15.92 ns**；
2. 利用率只有约 21%，因为 773 个并行 IO 把 die 撑到了 0.64 mm²；
3. 流程 `flow_status` 显示 failed——后来查明是第 37 步 chroot 环境里 KLayout 崩溃（工具自身 bug），与设计无关，第 36 步 GDS 早已正常产出。

第一版的价值不是指标，而是**证明了链路可行**，并且用真实数据定位了瓶颈。

### v2：砍 IO，切流水

针对短板，做两件事：顶层从 773 并行 IO 改为 **32-bit 串行接口 + start/busy/done 握手**；压缩核拆成 **二级流水**——第一级算 W 扩展，第二级算 t1/t2 并更新 A–H。

中间踩了坑：第一次把 die 调到 550，布线直接拥塞 fatal（GRT-0119）；调到 700 仍然拥塞。最后找到 OpenLane 1.1.1 的合法参数 `GRT_ALLOW_CONGESTION="1"` + `GRT_OVERFLOW_ITERS="200"`，让详细布线自己收敛。

结果：**53.45 MHz（+38%）、0.49 mm²（-23%）、利用率 33.53%、0 违例、布线器估算 WNS = 0**。

一代之内，频率涨了近四成、面积缩了四分之一，这一代是收益最猛的。

### v3：继续切，但开始看清边界

第三版把压缩核再细分为三级：

- phase0：只算 W 扩展 `wc`
- phase1：并行算 `t1p = H + Σ1 + Ch + K`、`t2p = Σ0 + Maj`
- phase2：更新 `E = D + t1p + wc`、`A = t1p + wc + t2p`

三级之后，**58.17 MHz**，只比 v2 高 9%。

这里出现了本项目最重要的一次认知转折：单级组合逻辑已经压到约 **6.6 ns**，但 signoff 关键路径周期是 **17.6 ns**——中间近 11 ns 的差额，根本不是组合逻辑，而是**寄存器 CK-to-Q 延迟 + 布线 RC 互连**。

也就是说，130nm 工艺下，当组合逻辑被切得足够细，瓶颈就从"算得慢"变成"寄存器和连线本身就很慢"。这是该工艺的物理上限，再切流水级也没用。频率曲线开始边际递减：+38% → +9%。

### v4：不再堆频率，改做面积

既然频率已经接近工艺天花板，第四代换了目标：把 die 从 700×700 收到 **640×640**，硬冲利用率 40%。

结果：**56.72 MHz、0.41 mm²、利用率 40.65%、仍 0 违例、布线器估算 WNS = 0**。

代价是频率回落 1.45 MHz——die 收紧后布线更密，SPEF WNS 从 -7.19 变成 -7.63。但换来的是利用率 +21%、面积 -16%。

这一代的意义在于：**它不再是"优化参数"，而是"做取舍"**。知道什么时候该停、该换维度，比会调参数更接近工程师的思维。

### v5：把约束改对，让时序真正签核通过

v1–v4 有一个始终没解决的问题：跑完 flow 后 `optimized_wns = 0`，看起来很漂亮，但那是**布线后 resizer 基于预估寄生的估算值**。用 RCX 提取真实 SPEF 重跑三 PVT corner STA，四代 setup 余量全是负的，v4 nom 是 **-7.63 ns**，hold 最差 -0.45 ns。按签核标准，这四代都不合格。

排查下去发现了根因：`config.tcl` 里的 `CLOCK_PERIOD` 从第一天起就写着 **10.0 ns（100 MHz）**。这是"我想要"，不是"工艺能给"。actual 频率 56.72 MHz（周期 17.63 ns）意味着约束比实际能力激进了一倍多，resizer 一直在为一个达不到的目标做过度优化，签核自然崩。

v5 不改一行 RTL、不动 die、不换综合策略，只做两件事：

1. `CLOCK_PERIOD` 从 `10.0` 改成 `26.0`（依据：v4 signoff period 17.63 + WNS 7.63 = 25.26，取整 26）
2. 给 resizer 加余量：setup 0.30 ns、hold 0.40 ns

结果是三 PVT corner 全部转正：

| corner | WNS | TNS | setup worst slack | hold worst slack |
|---|---|---|---|---|
| rcx_min | 0.00 | 0.00 | +5.00 ns | +0.43 ns |
| rcx_max | 0.00 | 0.00 | +3.12 ns | +0.44 ns |
| rcx_nom | 0.00 | 0.00 | +4.03 ns | +0.43 ns |

**这是这个项目第一次拿到干净的时序签核结果。**

代价也很清楚：频率回落到 **38.46 MHz**（-32%），功耗降到 6.31 mW，布线 DRC 仍为 0，利用率升到 45.18%，GDS 43.4 MB，XOR 40 层零差异。换句话说，v5 不更快，但它是**第一个能拿去签核的一代**。

这一代真正教会我的是：**约束该跟着工艺走，不该跟着愿望走**。四代负余量不是设计缺陷，是我一开始就把靶子画错了地方。

### v6：只压约束，测出余量还剩多少

签核通过之后有个问题没回答：v5 的 +5.00/+4.03/+3.12 ns 余量，到底是真的富余，还是取整 26.0 ns 恰好赶上的运气？

v6 的做法是单变量对照：v5 的全部配置一字不动，只把 `CLOCK_PERIOD` 从 `26.0` 改成 `24.0`（41.67 MHz）。RTL、die、综合策略、resizer 余量、GRT 参数全部相同。

| corner | WNS | TNS | setup worst slack | hold worst slack |
|---|---|---|---|---|
| rcx_min | 0.00 | 0.00 | +3.08 ns | +0.43 ns |
| rcx_max | 0.00 | 0.00 | +1.25 ns | +0.43 ns |
| rcx_nom | 0.00 | 0.00 | +2.12 ns | +0.43 ns |

三 corner 仍全为正，最紧的 setup 余量收窄到 **+1.25 ns**，hold 稳定在 +0.43 ns。物理指标几乎没变：利用率仍 45.18%、12,288 cells、DRC 0，线长 801,019 µm、通孔 124,397，GDS 43.3 MB，runtime 先降到 40 分钟。

**关键结论**：把最紧角余量（1.25 ns）加回周期，得可达周期约 **22.75 ns（≈43.9 MHz）**。这就是这条 RTL 在 sky130A 上的定量边界——再往下压就进入负余量区，只能改 RTL 或改工艺，调约束已经没有空间。

所以 v5 和 v6 是一对方向相反的实验：v5 证明"约束写错了就签核不过"，v6 证明"约束写对了，能撑到 43.9 MHz"。两条合起来，才把这个设计的真实能力区间测清楚。

### v7：换掉结构，而不是继续压约束

v6 给出的 43.9 MHz 是**这条 RTL** 的边界，不是工艺的边界。所以第七代没有再动约束，而是动结构：把消息调度从 **16 深循环窗口**换成**移位寄存器**，同一块 640×640 的 die，不加面积。

结果：**55.56 MHz（+33%）**，cells 反而从 12,288 降到 **11,475**，功耗 9.41 mW，面积 0.4096 mm²。

这一代推翻了项目早期文档里那句"43.9 MHz 是这条 RTL 的上限"——那只是旧架构的上限。**约束调不动的时候，要改的是结构。**

物理实现上这一代第一次做到 **0 布线违例与可交付 GDS 落在同一次 run**：GDS 40,396,222 字节，2,983,020 个多边形；双工具逐层 XOR 七代全部 PASS，40/41 层共同层零差异，唯一差异是标定层 (81,14)（不参与制造，流水线本身也把它排除）。

## 三、把"流水线没跑成的那几步"补回来

前六代都卡在同一个地方：第 37 步 KLayout 在 chroot 里崩溃（`tlFileUtils.cc:979`），于是 XOR、KLayout DRC、密度这些检查从来没在流水线里跑成过，`metrics.csv` 里对应列一直是 `-1`——**是"没跑"，不是"0"**。这一节记录我怎么把它们一个个补出来，以及每个结论的边界。

### 1. 崩溃真因：`/proc` 是空目录

前几次认定"KLayout 在 chroot 里必崩"，其实查错了方向。`tlFileUtils.cc:979` 的断言来自 `get_app_path_internal()`——它只查 `/proc/<pid>/exe` 来定位自己的可执行文件，而 chroot 挂进去的 `/proc` 是个空目录。把那个路径造出来再 `exec` 一次就通了：

```sh
P=$$; mkdir -p /proc/$P; ln -sfn "$BIN" /proc/$P/exe; exec "$BIN" ...
```

`exec` 不换 pid，所以软链一直有效。这不是"绕过检查"，是把工具依赖的运行环境补齐。

### 2. KLayout signoff DRC：218 个规则类、0 条

同一份 GDS、同一个 PDK deck，跑出 **218 个规则类、0 条违例**，93.690 秒。但"0 条"必须配正对照才算数：我造了一个故意违规的版图（两条 met1 间距 0.10 µm），同一 deck 同一参数报出 1 条 `m1.2`——证明引擎确实在查这份版图，而不是空转。

还有一个必须写明的细节：**0 条时的报告与上一轮逐字节相同**（34,074 字节）。这不是"两次结果一样"，而是空报告只写类别表、不写条目，同一 deck 跑两次必然同字节。所以哈希不能当"跑过"的凭证，凭证是日志里的输入路径与耗时（106.120 s → 93.690 s）。

顺带查出一处上游不一致：deck 读的是 `$top_cell` 与 `$thr`，而 OpenLane 的 `run_klayout_drc_sky130` 传的是 `topcell=` / `thread=`。照上游那套只传一组，两个值都会静默落到默认（自动选顶层、固定 4 线程）。我这次两个名字都传，`<top-cell>` 行可查确实是 `sha256_axil`。

### 3. 金属密度：六层 0 条

密度是另一份 deck（`met_min_ca_density`），查的是"金属太密"而不是"太稀"。六层空孔率：

| 层 | 空孔率 | 阈值 |
|---|---|---|
| li1 | 0.4993 | ≥ 0.40 |
| m1 | 0.7275 | ≥ 0.40 |
| m2 | 0.9055 | ≥ 0.40 |
| m3 | 0.9264 | ≥ 0.40 |
| m4 | 0.9460 | ≥ 0.40 |
| m5 | 0.9763 | ≥ 0.24 |

全在阈值之上、0 条，5.780 秒。同样带正对照：把 met1 铺满整个 die，同一 deck 报 1 条 `m1.pd.1d`。这份报告 `items` 为空、`categories` 也为空，本身就是 PASS 形态——空报告长这样，得在文档里写清楚，否则下一次会误判成"没跑"。

### 4. 天线：从 67 个 net / 87 个 pin 越限修到 0

用 OpenLane 自己的 OpenROAD `check_antennas` 对布线后的 ODB 补跑，原始状态报 **67 个 net / 87 个 pin 越限**——原因是那一版 `DiodeCells = 0`，一个二极管都没插。

修法不是"改工具"，是补上我自己漏掉的开关：从 `22-global.odb` 出发，跑 `global_route` 时必须带 `-allow_congestion`；OpenLane 只在 `GRT_ALLOW_CONGESTION=1` 时才传它，而那个 run 的配置里正是 1。我前五次手写脚本漏了这个开关，才一再撞 `DRT-0218` / `GRT-0226`，由此得出的"工具走不通"结论已经撤回。

三轮共插 **430 个二极管**，复测 **0 / 0**，流出新 GDS 18,618,660 字节。这一版上重跑了 KLayout DRC（218 类 0 条）、密度（六层全过 0 条）、Magic DRC（`No errors found`），netgen LVS 原文 `Final result: Circuits match uniquely.`，两侧 15,588 器件 / 15,645 网相等。

**但这仍然只到"布线级修好"**：功耗、XOR、ERC、iRdrop 没在这一版重跑，所以上面那些功耗与 XOR 数字仍属于未修版，不能挂到这张新图上。

### 5. 时序：从"布线器估算"换成 RCX 真寄生

前四代的 `optimized_wns = 0` 是预估寄生的结果。换成 OpenROAD rcx 从 DEF 直接提寄生（`-lef_res`，max/nom/min 三份规则各写一份 SPEF），三个工艺角各算一次，最差 setup **+0.4058 ns**（Slowest）、最差 hold **+0.4096 ns**（Fastest）、TNS 0——18 ns 周期成立。

同一套脚本拿去跑旧版官方产物，能复现此前公布的 **+0.5619**，说明口径没换。这里要撤回一条旧数：上一版写过的"估算口径 +9.8329 → +9.9243"过于乐观，不能当签核，已作废。

### 6. DRV：时序过了不等于签核过了

同一版上补查设计规则（DRV），**没过**：SDC 要求 `max_transition 0.75`、`max_fanout 10`，新版 Slowest 有 255 条 slew、219 条 fanout 违例（最差 slew 1.17、最差扇出 27）。旧版同脚本也早有 210 / 143 条、最差扇出 25——所以这不是新版引入的，但也不能因此说"通过"。

根因追到了行：`config.tcl` 第 10 行时钟扇出目标 16、第 29 行 sink 聚类 25，而生成的 SDC 卡 10，**配置自相矛盾**。按根因改参数重跑 CTS，扇出违例 143 → 9；残留 9 条我一度归因到工具内部"每簇最多 15 sink"的判据上——**这条后来被我自己的数据推翻**：聚类 size 9 + 直径 80 时扇出违例直接是 **0**（最大扇出正好等于限值 10），面积还小了 76 u²。

### 7. 整条 flow 重跑一次：所有结论落在同一版上

上面每一条都是"在流水线之外拼零件"。于是最后一步是把参数写进设计 `config.tcl`，让整条 OpenLane flow 从头跑一次（tag `ctsfix3`），同一次 run 出 GDS，同一份 GDS 出 LVS、DRC、密度。

改的是四行：`CTS_SINK_CLUSTERING_SIZE "9"`、`CTS_SINK_CLUSTERING_MAX_DIAMETER "80"`、`GRT_REPAIR_ANTENNAS "1"`、`RUN_KLAYOUT "0"`（就是上面那个 `/proc` 问题的规避，XOR 改到宿主机上做）。

| 项 | 结果 |
|---|---|
| CTS 扇出 | sink 248，分布 `9:244, 10:2`，上界等于 SDC 的 `set_max_fanout 10` |
| 详细布线违例 | 12,932 → 4,974 → 4,733 → 1,076 → 79 → 34 → 1 → 1 → **0** |
| GDS / 网表 | 40,396,222 B / 3,379,950 B |
| 走线 / 过孔 / 单元 / 利用率 | 618,229 µm / 117,592 / 47,559 / 46.20% |
| 时序三 corner | setup **+0.51 / +0.74 / +0.99 ns**、hold **+0.41 / +0.41 / +0.40 ns**，全 MET |
| LVS | `Circuits match uniquely`，151 处叶子单元逐个匹配，两侧各 34,182 实例 / 36,256 器件 |
| KLayout DRC | 218 类 / **0 条**（正对照报 1 条 `m1.2`） |
| 金属密度 | 六层 0.4993 / 0.7275 / 0.9055 / 0.9264 / 0.9460 / 0.9763，**0 条**（正对照报 1 条 `m1.pd.1d`） |

这一版的 GDS 是 40,396,222 字节（sha256 `0cb148d6…`）。LVS 之前卡了四轮，每轮都是真缺陷：fill/tap 在版图里没有器件却被展平成 unmatched；电源引脚口径没对齐（`VNB→VGND`、`VPB→VPWR`）报出 13,961 个 `Net:` 片段；Magic 写出的网表按固定列宽折行，续行让按行首统计的脚本数错实例；CTS 加的 `clkload*` 悬空输出在版图侧被命名成 `clkload90/X`、网表侧写成 `NC_Y` 这类常量名，178 个悬空输出被归成一类、报 222 个 Net mismatch。两侧统一按"实例/引脚"命名后归零。

**这一版仍不是"签核通过"**：`metrics.csv` 的 `flow_status` 是 `flow failed`——第 36 步"Magic Spice Export from LEF"在 chroot 里假死（15 分钟 CPU 只跑 17 秒、打开的文件描述符停在 155 不增长），LVS 是在 flow 之外用同一份 GDS 单独跑的（已固化成 `tools/lvs/run_lvs.sh` 一条命令，末行打 `LVS PASS`）。所以 `lvs_total_errors`、`Magic_violations`、`pin_antenna_violations`、`net_antenna_violations`、`klayout_violations` 五列仍是 `-1`。天线复检这一步没跑到（配置里 `GRT_REPAIR_ANTENNAS` 是开的，但 signoff 的 antenna 检查没执行），**天线这一项我不给结论**；GDS XOR 这一版也没跑。准确说法是：这一版第一次同时具备"布线 0 违例"与"可交付 GDS + LVS 通过 + DRC / 密度补跑 0 条"，缺的是天线复检与 GDS XOR 两项。

## 四、踩过的坑（这部分可能比指标更有用）

**1. 网络是第一道墙**
本机 Docker Hub 认证域全超时、国内镜像 401、GitHub 大文件被限速到 15~30 KB/s。三条本地部署路线实测全部死路，最后只能上云主机、用 chroot 跑 OpenLane rootfs。

**2. 启动目录必须是 `/designs`**
在 `/designs/sha256` 目录里启动 flow，prep 阶段 100% 报 "Design not found" 并 `exit(-1)`。必须 chroot 进 `/designs` 根目录再跑。

**3. 漏一个环境变量就挂**
`TERM=xterm NO_COLOR=1 LC_ALL=C LANG=C PDK_ROOT=/pdk` 一个都不能少。有一次漏了 `LC_ALL=C LANG=C`，STEP 0 verilator lint 直接因 locale 崩掉，GDS 都没产出。

**4. chroot 里 KLayout 崩，不是"必崩"，是 `/proc` 空**
`tlFileUtils.cc:979` 是找不到 `/proc/<pid>/exe` 的断言。造出那个路径再 `exec` 就能跑，DRC 与密度都因此补上了；不想动环境就把 `RUN_KLAYOUT` 关掉，XOR 放到宿主机做。

**5. 拥塞别硬调 die**
`GRT-0119` 不是让你无限放大 die 的。用 `GRT_ALLOW_CONGESTION` + 提高溢出迭代次数，让布线器收敛，比盲目加尺寸划算。反过来，手写脚本重跑布线时漏传 `-allow_congestion`，会得到"详细布线无解"的假结论。

**6. 版图渲染要跳填充层**
用 gdspy + matplotlib 渲染时，金属填充层和铺满层会把图糊成一片绿色，只渲染结构层（本项目用 64/65/69/70/71/72 层）才看得清布线。

**7. 流程"失败"不等于设计失败**
`flow_status: failed` 是 KLayout / Magic 导出两个工具步骤在 chroot 里出问题，GDS 与全部指标都有效。要学会读日志、区分工具 bug 与设计问题——但也不要因此把 `-1` 说成 `0`。

**8. 0 条要有正对照，0 条报告会同字节**
空报告只写类别表，同一 deck 跑两次必然同字节，哈希相同不代表"跑过两次"。判"跑过"只能看日志里的输入路径、命令行参数与耗时。

## 五、结论与边界

**技术结论：**

- 七代设计全部 **0 布线 DRC 违例**（v4 经 14 轮迭代从 16,283 收敛到 0）
- **v5–v6 三 PVT corner 时序签核全通过**：WNS 0.00、TNS 0.00；v5 setup 余量最少 +3.12 ns、v6 最少 +1.25 ns，hold 均 +0.43 ns；功耗 6.31 mW / 6.84 mW
- **v7 同 die 提到 55.56 MHz**（+33%），cells 从 12,288 降到 11,475，功耗 9.41 mW，面积 0.4096 mm²
- **rcx 真寄生 STA（18 ns）**：最差 setup **+0.4058 ns**、最差 hold **+0.4096 ns**、TNS 0
- **整条 flow 重跑那一版（ctsfix3）**：布线 0 违例、LVS `Circuits match uniquely`（两侧 34,182 实例 / 36,256 器件）、setup +0.51 / +0.74 / +0.99 ns、hold +0.41 / +0.41 / +0.40 ns、KLayout DRC 218 类 0 条、金属密度六层 0 条——**全部落在同一版 GDS 上**
- 三层验证全通过：逻辑 11/11、核心仿真 12/12、顶层握手 3/3，锚点向量 `abc`/`empty`/`fox` 摘要逐位一致
- 七代 GDS 双工具 XOR 校验全部 PASS（40/41 层共同层零差异，唯一差异为标定层 81/14）
- 58 MHz 是 130nm 工艺下这颗设计"能跑但签核不过"的极限；24–26 ns（41.67 / 38.46 MHz）是"真能签核"的工作点；43.9 MHz 是旧架构的约束边界，换调度结构后这个边界被推到 55.56 MHz
- 从 0.64 mm² 到 0.4096 mm²、从 21% 到 46.20% 利用率，证明架构与面积两手都要会

**诚实边界：**

- 这不是量产芯片，没有商业价值；它是**作品集**和**方法论验证**
- **v1–v4 时序没有收敛**：SPEF 重签核后 setup 余量都是负的（v4 nom -7.63 ns），hold 最差 -0.45 ns。那四代严格按签核标准不合格——这一点必须写清楚，否则就是把"布线器估算"当成"签核结果"。**v5 解决了它，但用的是降低频率，不是提高设计能力**
- **时序过了不等于签核过了**：同一版上补查 DRV，Slowest 还有 255 条 slew、219 条 fanout 违例（最差 slew 1.17、最差扇出 27）。准确说法是"时序通过、DRV 未清"。改成聚类 size 9 之后扇出归 0，但 slew 这一类没有在 ctsfix3 上重新逐条核过
- **ctsfix3 那一版仍缺两项**：天线复检没跑到（`GRT_REPAIR_ANTENNAS` 虽然开着，signoff 的 antenna 检查没执行，本页不给结论）、GDS XOR 没跑
- **`metrics.csv` 里那五个 `-1` 是"没跑"，不是 0**：`lvs_total_errors`、`Magic_violations`、`pin_antenna_violations`、`net_antenna_violations`、`klayout_violations`
- v6 已经把加压收敛做到 24.0 ns 并保持三 corner 全通过；没有做 DFT 插入与 ECO；功耗只在部分版本取过，没有逐版对比

**真正的价值在哪：**

不是这颗芯片，而是"**一个人、零成本、把 RTL 做到 GDS，再把每个结论追到证据文件的一行**"这件事本身。芯片行业门槛高，但完整闭环的门槛，其实没想象中那么高——只要你愿意接受开源工艺、愿意读日志、愿意承认边界。

技术定稿之后，下一步的加分项不在性能，而在**呈现**：开源发布、README、技术博客——让这套东西被看见、被验证、被引用。

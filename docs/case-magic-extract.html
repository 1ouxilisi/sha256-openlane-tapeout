magic 为什么在 extract 时无限等下去

这是一个真实卡住、又被定位到文件系统层面的问题。不讲设计思想，只讲怎么从「卡住不动」一步步挖到根因、 给出能跑的修法。如果你在 OpenLane 里遇到过「流程跑到某一步就不动、CPU 几乎为零、不报错也不退出」， 这一页就是为你写的。

一、先看症状：没有报错，才最难查

流程卡在 magic 的 spice 提取这一步（OpenLane 的 extract_spice.tcl）。下面每一项都是当时能直接观察到的，不是事后推测。

观察项读数 / 现象
卡住位置magic spice 提取，日志停在处理顶层 cell，不再往下走
CPU 占用几乎为 0 —— 不是算力不够，也不是死循环打满
内存稳定、不增长 —— 不是内存耗尽
报错信息没有任何 error，进程不退出
等待时长无限。放一晚上回来，还停在原地

没有报错就意味着没有现成线索。这时候最容易做的事是杀掉重跑、再杀再重跑——但根因不变，重跑只会在同一位置再卡一次。所以先不重跑，先判断它到底在「算」还是在「等」。

二、先排除三种常见误判

每排除一种，方向就收窄一步。

① 不是死循环 / 死锁占 CPU

如果是死循环，CPU 会被打满。实测 CPU 几乎为 0，说明进程在等待某件事，而不是在计算。这把方向从「逻辑算错」转到「在等资源」。

② 不是内存不足

内存耗尽时，进程要么被内核的 OOM killer 杀掉，要么自己报错退出。实测内存稳定、进程仍然活着，排除内存问题。

③ 不是 magic 整个坏了

拿单个 cell，用绝对路径加载再 extract，能正常产出一个 856 B 的 .ext。引擎本身工作正常，问题出在特定的工作方式上，不是程序崩了。

收窄后的判断

一个活着、不占 CPU、不报错、又不退出的进程，基本可以断定它在等一个它认为会出现的东西——一个文件，或者一次回应。下一步就去看它在内核里到底等在哪个函数上。

三、进程层面的证据：它在等什么

Linux 下每个进程在 /proc 里都有状态。把状态读出来，「卡住」就变成了具体的读数。

指标读数含义（讲清楚语法）
stateSS 是可中断睡眠（interruptible sleep）。进程没在运行（运行是 R），它在等某个事件或资源，等到了会被唤醒。
wchanrequest_wait_answerwchan 是 wait channel，即内核里进程正等待的那个函数的名字。这个名字说明它在等一次「回答」——结合 magic 的行为，是在等一次文件查找的结果。
voluntary switch每秒约 1,000 次voluntary context switch 是进程主动让出 CPU 去等资源。每秒上千次，说明它在反复「问一下、没有、睡、再问」。

再看系统调用层面，能观察到它反复调用 openat，去各个搜索路径下打开同一个文件 sky130_fd_sc_hd__tapvpwrvgnd_1.ext，每次都返回 ENOENT（文件不存在），然后换一个路径再找。到这里，「它在等什么」就被具体化成了一个文件名。

四、根因：incremental 模式找不到文件，又不肯现场提取

magic 的两种 extract 方式

方式行为
裸 extractincremental（增量）模式。它假设子 cell 的 .ext 已经存在，直接复用；不存在就沿搜索路径去找。
extract all递归地把 root 和所有 children 现场提取一遍，按依赖顺序生成，不依赖任何预存文件。

为什么偏偏是这个 cell

sky130_fd_sc_hd__tapvpwrvgnd_1 是一个 physical-only 单元——只做阱连接和电源钳位，没有逻辑功能。这个设计里它有 5,496 个实例。

而 PDK 的事实是：它只发布 .mag（版图源文件），不发布 .ext。.ext 本来就是 magic 在本地提取时生成的中间产物，不该由 PDK 提供。

关键缺陷在这里：incremental 模式沿 cell 基路径和全部搜索路径找 .ext 全部失败后，没有回退成「那我现场提取这个子 cell」，而是无限重试。于是进程停在 S 状态，反复 openat、反复 ENOENT，永不自救。

历史上 ctsfix3 那次 run 就死在完全相同的位置，当时以 child killed 结束。是同一根因，只是那一次没有挖到文件系统这一层，把它当成了偶发的子进程被杀。

五、对照实验：先证死，再动手修

修之前先做三组对照，确认修法方向是对的，而不是换个姿势碰运气。

操作结果说明
单 cell，绝对路径 load 再 extract正常，出 856 B 的 .ext引擎没坏，现场提取这条路是通的
裸 load 一个 cell 名（不带路径）只打印 Creating new cell，建了个空 cell名字解析找不到 PDK 里的真实 cell，反向印证路径的重要性
把缓存 .ext 拷进工作目录再跑能过证明它确实只认预存文件；有文件就走，没有就卡

三组对照指向同一个修法方向：让 magic 不依赖预存 .ext，也就是让它现场递归提取全部子 cell。

六、修法与验证

下面是修复脚本的关键部分，是真实跑过的代码，不是示意。

# 提取选项（与 OpenLane extract_spice.tcl 保持一致）
extract do local
extract no capacitance
extract no coupling
extract no resistance
extract no adjust

# 关键修复：用 extract all 代替裸 extract
extract all

# 转 LVS spice 网表
ext2spice lvs
ext2spice -o $EXT_NETLIST $TOP

extract all 的作用是显式递归提取 root 加全部 children，magic 按依赖顺序现场生成每个 .ext，不再去找一个 PDK 本来就不提供的文件。

验证项结果
干净目录重跑一次跑过，不再卡住
产出 .ext153 个，顶层 .ext 为 17,151,056 B
LVS 网表ext2spice 出 3,463,849 B 的 spice
netgen LVS两侧 15,873 器件 / 15,795 网相等，Final result: Circuits match uniquely；badnets、badelements 均为空

这个修复跟具体设计无关。任何 sky130A + OpenLane 1.1.1 + magic 8.3.483 的 run，只要用到 physical-only 的 tap 单元，都会撞上同一根因。所以修法脚本随 Release 公开，而不是藏在自己的 run 目录里。

七、边界：我只对这一个根因负责

  • 验证过的组合是 magic 8.3.483 + OpenLane 1.1.1 + sky130A。不同 magic 版本的 extract 行为可能不同，升级版本前请先在单 cell 上验证。
  • extract all 会比 incremental 慢，因为要现场提取全部子 cell。这是用确定性换速度，不是免费的。
  • 它解决的是「提取卡住」，不解决「LVS 不匹配」。LVS 匹配是另一条独立证据链，这里只保证网表能被正确生成。
  • 我不声称这是 magic 的唯一问题，只对这一个被完整复现、修复并验证的根因负责。

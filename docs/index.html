零成本把 SHA-256 从 Verilog 做到 GDS

没有商业 EDA 授权，没有流片预算，没有制造排期。用 OpenLane 1.1.1 与 SkyWater 130nm 开源 PDK， 把一颗 SHA-256 加速器真实地做到可打开的 GDSII 版图 —— 七代迭代，每代解决一个真问题， 最后换掉消息调度结构，把“这条 RTL 到 43.9 MHz 就到底了”这句话亲自推掉。

七代演进：每代只解决一个问题

不是调参刷数字。每一代的起点都是上一代暴露的一个具体缺陷。

v1 · 先把链路跑通tapeout6

单块组合逻辑、773 个并行 IO、不做流水线。38.58 MHz / 0.64 mm² / 利用率 20.99%，布线 0 违例。 用 RCX 真实寄生重签核后 WNS -15.92 ns —— 这一代的价值不是指标，是证明链路可行，以及暴露了三个短板：无流水线、IO 撑大 die、利用率只有两成。

v2 · 砍 IO，切两级流水tapeout9

顶层改成 32-bit 串行接口 + start/busy/done 握手，压缩核拆两级。中途 die 收到 550 直接拥塞 fatal， 最终靠 GRT_ALLOW_CONGESTION=1 + GRT_OVERFLOW_ITERS=200 让布线器收敛。 53.45 MHz（+38%）/ 0.49 mm²（-23%）/ 利用率 33.53%，收益最猛的一代。

v3 · 三级流水，撞见工艺墙tapeout10

压缩核再细分三级。58.17 MHz，只比 v2 高 9%。这里出现本项目最重要的认知转折： 单级组合逻辑已压到 6.64 ns，而签核关键路径是 17.19 ns —— 中间 10 ns 不是逻辑，是寄存器 CK-to-Q 加布线 RC。 瓶颈从"算得慢"变成"寄存器和连线本身慢"，再切流水没有意义。

v4 · 不再堆频率，改做面积tapeout12

die 从 700×700 收到 640×640，硬冲利用率。56.72 MHz / 0.4096 mm² / 40.65%，14 轮迭代把 DRC 从 16,283 收敛到 0。 代价是频率回落 1.45 MHz、WNS 从 -7.19 变 -7.63。这一代的意义是"做取舍"：知道何时该停、该换维度。

v5 · 把约束改对，让时序真正签核通过tapeout13

前面四代 flow_status 显示的 optimized WNS = 0 是 resizer 估算值，不是签核值。用 RCX 真实 SPEF 跑三 PVT corner， v1–v4 的 setup 余量全是负的。根因：config.tcl 里 CLOCK_PERIOD 从第一天就写着 10.0 ns（100 MHz 的愿望）， 而实际只到 56.72 MHz —— 约束比工艺能力激进一倍多。 不改 RTL、不动 die、不换策略，只把周期改成 26.0 ns 并给 resizer 加余量： 三 corner 全部转正（WNS 0.00 / TNS 0.00 / setup +5.00、+4.03、+3.12 / hold +0.43），功耗 6.31 mW。

v6 · 只压约束，测出余量还剩多少tapeout14

v5 余量是真富余还是取整碰巧？v6 把 v5 配置一字不动，只把周期从 26.0 改成 24.0 ns（41.67 MHz），干净的单变量对照。 三 corner 仍全为正：+3.08 / +2.12 / +1.25 ns，hold 稳定 +0.43，功耗 6.84 mW（+8.4%，频率 +8.3%，基本线性）。 把最紧角 1.25 ns 加回周期，得 22.75 ns ≈ 43.9 MHz —— 这就是这条 RTL 在 sky130A 上的定量边界。 但它只是"这条 RTL"的边界，v7 把它推掉了。

v7 · 换结构，而不是继续试探约束tapeout15 / tapeout16

前六代都在同一套 RTL 上压约束。v7 换掉消息调度：W 从 16 深循环窗口（(t-k)%16 动态索引）改成 16 级移位寄存器， 索引退化为固定连线，mux2_2 从 2,239 降到 685（mux 总数 -64.5%），逻辑单元 12,288 → 11,475。 同时加 h_in/h_out 链值接口做多块流式，顶层换成 AXI4-Lite 从接口。

先在 24.0 ns 跑一代做可比对照：面积小 6.6%，三 corner 余量从 +1.25 放大到 +6.44，说明关键路径真的短了。 于是再压到 18.0 ns：三 corner 仍全正（+1.03 / +0.80 / +0.56，hold ≈ +0.40，TNS 0）， 55.56 MHz —— 同一块 0.4096 mm² 的 die、同一个库、同一个时钟端口，比 v6 快 33%。

代价如实记：功耗 6.84 → 9.41 mW（频率 +33%，单位频率功耗基本持平），v7 买到的是更快、更小、能集成，不是更省电。

验证：五层可核对的证据

正确性有绝对标准 —— SHA-256 的输出可以用 Python hashlib 逐位比对。

L1 · 逻辑对照

11/11 PASS。RTL 行为模型与软件实现在同一批输入下逐位一致。

L2 · 核心仿真

12/12 PASS。iverilog 跑 12 组测试向量，覆盖空串与边界长度。

L3 · 顶层握手

3/3 PASS（v1/v2 为 2/2）。start / busy / done 时序与串行接口对齐。

物理 · 版图一致性

七代全部 PASS。Magic 与 KLayout 双 GDS 逐层 XOR，40/41 层共同层 0 差异，唯一差异是标定层 (81,14)。

L3+ / L4 · v7 新增

压缩核 3/3 PASS（abc / empty / fox，含一条"v6 与 v7 同输入并排跑逐位一致"的对照）；AXI4-Lite 顶层 2/2 PASS（含两块流式链值）；verilator 5.018 --lint-only -Wall 对 v7 是 0 error / 0 warning。

锚点向量：abc = ba7816bf…、空串 = e3b0c442…、fox = d7a8fbb3…，全部逐位一致。

不止这里写着 PASS —— 你自己跑一遍

两条命令即可复现本页的功能结论，不需要 OpenLane、不需要 PDK、不需要云主机：

bash scripts/verify.sh
python3 scripts/check_vectors.py

前者用 iverilog 编译 RTL + testbench，跑 abc / empty / fox 三条锚点向量，输出 ALL TESTS PASSED；后者用 Python hashlib 独立复算期望值，避免“自己验自己”。两步同样跑在 GitHub Actions 上（.github/workflows/verify.yml），每次 push 都在干净 runner 里重跑。

再往上一层是可选的综合对照：bash scripts/synth_check.sh（需本地 yosys 与 sky130 liberty）把同一份 RTL 独立映射到 sky130_fd_sc_hd，v6 得到 9,248 cells；而本页记录的 12,288 cells 里有 2,532 个是 buf_1，剔掉 buffer 后净逻辑约 9,756——两者相差 5%，说明这个数字不是流程黑箱，换掉 OpenLane 也能得出同量级网表。v7 我也用同一条流程复跑了一次，结论是这个对照不成立：不加 DFF 库映射时 v6 得 9,248、v7 得 14,375；补上 dfflibmap 后 v6 得 10,842、v7 得 11,604——两套结果与 OpenLane 的 12,288 vs 11,475 符号相反。说明裸综合的可比性取决于有没有做 DFF 库映射和用什么 abc 策略，它只够证明“这条 RTL 能独立综合进 sky130 标准单元库”，不足以用来判断 v6 与 v7 谁更小。这里把失败的复现如实写出来，而不是只留 v6 那次漂亮的数字。

还有一个更硬的层次：bash scripts/verify_driver.sh 把软件侧驱动拉进验证链——C 驱动打出寄存器写序列 → Verilog 主机模型把该序列原样发到真 RTL 的 AXI4-Lite 总线上 → Python hashlib 独立算期望摘要，三份实现互不依赖；四条消息（abc / 空串 / 119 字节两块流式 / fox）全部 PASS，并作为 CI 的第 6 道门每次 push 自动重跑。这一层不用"作者自己写的期望常量"作判据，所以它同时回答了"别人能不能接手"。

如果不懂芯片但需要判断这份交付物真假，看 验收手册：六个真实踩过的坑（功耗角名标错、拿 resizer 估算当签核、"43.9 MHz 是工艺上限"、独立综合口径符号相反、flow_status 失败不等于没有 GDS、换个环境就复现不了）、六条通用验收动作，以及一张"你不需要懂什么"的边界表。

边界：这一页不写的东西

不是量产芯片。作品集与方法论验证，商用价值为零 —— SHA-256 加速器本身没有稀缺性。

v1–v4 时序确实没收敛。SPEF 重签核后 setup 余量全负（v4 nom -7.63 ns），按签核标准不合格。不写这一点，就是把估算当签核。

v5 的通过靠的是降低频率，不是提高设计能力。38.46 MHz 不代表性能强，它是在该工艺下"真能签核"的工作点。

22.75 ns 是"v6 那套 RTL"的边界，不是工艺边界。v7 换掉消息调度后，18 ns 三 corner 仍全正余量（最紧 +0.56 ns）。把架构上限说成工艺上限，是这个项目前六代差点犯的错。

v7 没有变省电。频率 +33%、功耗 +37%，单位频率功耗基本持平；每块能耗反而更差。它不是能效优化的一代。

吞吐仍然很低。约 15 MB/s，比带 SHA-NI 的 CPU 慢两个数量级；多块流式省的是软件搬运，不是算力。padding 仍由软件完成。

未做 DFT 扫链插入，未做 ECO。距离"可测、可修"的量产流程还差两环。

七代 flow_status 均为 failed，唯一原因是 STEP 37 在 chroot 内调用 KLayout 崩溃（tlFileUtils.cc:979，工具自身 bug）；STEP 36 已正常产出 GDS，全部指标有效。

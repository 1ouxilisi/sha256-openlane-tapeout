局部 ECO 清理 max_slew 违例：275 -> 60
SHA-256 Accelerator / sky130A / OpenROAD b16bda7e
实测时间：2026-11-13（云主机 4 核 / 7 GB，chroot 内 openroad）

--------------------------------------------------------------------------
一、这件事要解决什么
--------------------------------------------------------------------------
tapeout 版（antclean_fill）在 Slowest 角上有 275 个 max_slew 违例
（约束 set_max_transition 0.7500 ns，SDC L212）。这不是功能问题，
是驱动能力与线载不匹配：违例全部落在高扇出网的长线上。目标是把它们清掉，
并且不能把已经收敛的布线质量弄坏。

--------------------------------------------------------------------------
二、方法：只动违例的那几条网
--------------------------------------------------------------------------
每一轮做同一件事，作用域只到“当前违例网”：

  1. 用 max SPEF 跑 STA，抓违例脚（report_check_types -max_slew -violators）
  2. 违例脚 -> 所在网（唯一化；275 个脚其实只压在 47 条网上）
  3. 只对这些网做 odb::dbWire_destroy 剥线，其余 15,536 条网走线全部保留
  4. global_route（met1-met5，layer adjustment met1 0.99 / met2-met5 0，
     全局 0.3，set_macro_extension 0）
  5. estimate_parasitics -global_routing
  6. repair_design -slew_margin N -cap_margin 20
  7. detailed_placement + check_placement + global_connect
  8. detailed_route（met1-met5，-droute_end_iter 32，-or_seed 42，2 线程）
  9. RCX 重抽 max SPEF（rules.openrcx.sky130A.max.calibre，-lef_res），
     再 read_spef 回 STA。验收一律以“落 SPEF 再读回”为准

--------------------------------------------------------------------------
三、先被证伪的路线：整片重布
--------------------------------------------------------------------------
把 15,583 条信号/时钟网全部剥线重布（DRC 收敛到 0 违例，用时 445,173 ms），
结果是寄生变差：

  总电容      旧 max SPEF 126.5 pF / 15,583 网
              整片重布   151.0 pF / 15,584 网        (+19%)
  逐网比值    median 0.994 / mean 1.519 / p95 2.045 / max 1949
  层用量      met3 10,040 -> 20,417，met4 1,159 -> 3,259，met5 24 -> 283
  Slowest     slew 275 -> 1,147，setup +0.4543 -> -0.0149

四组交叉对照（新库+旧SPEF / 旧库+新SPEF / 新DEF+新SPEF / 旧DEF+自抽SPEF）
排除了“抽取流程有问题”这一解释：旧 DEF 走我这套 RCX 抽出来复跑，得到
275 / 0 / 0.45，与基线逐值重合。结论是整片重布把走线挤到上层金属，
线电容涨 19%，slew 随之崩。

--------------------------------------------------------------------------
四、局部 ECO 的实测结果
--------------------------------------------------------------------------
口径：Slowest 角，旧/新 max SPEF 均为本机 RCX 抽取，格式统一为
      slew 违例数 / cap 违例数 / setup WNS / hold WNS

  基线（tapeout 库 + 旧 max SPEF）
      275 / 0 / +0.45 / +1.59      总电容 126.5 pF / 15,583 网，单元 22,015

  第 1 轮（剥 47 条网，repair -slew_margin 20）
      Found 82 slew，插 1 buffer in 41 nets，resize 27，cells 22,016
      DRT 115,652 ms，0 违例
      ->  102 / 0 / +1.37 / +1.33       总电容 126.5 pF / 15,582 网

  第 2 轮（剥 19 条网，repair -slew_margin 50）
      Found 148 slew，插 32 buffers in 74 nets，resize 9，cells 22,048
      DRT 76,308 ms（90 -> 1 -> 0 违例）
      ->   60 / 0 / +1.31 / +1.33       总电容 126.3 pF / 15,582 网

关键结论：这两轮把 slew 违例压掉 78%，而总电容从 126.5 pF 到 126.3 pF、
几乎没动；setup 与 hold 反而从 +0.45 / +1.59 变成 +1.31 / +1.33。
“局部 ECO 不破坏布线”这件事是被两轮实测确认的，不是假设。

--------------------------------------------------------------------------
五、为什么停在 60 而不是 0
--------------------------------------------------------------------------
剩下 60 个违例压在 12 条网上（最差 1.14 ns，5 个脚超过 1.0 ns，
23 个在 0.8-0.9 之间，其余在 0.75-0.8）。再往下走有两堵墙：

1) repair_design 在只有 GRT 估计、没有真实寄生时会按线载模型乱插 buffer。
   第 3 轮（60 个脚）它报 Found 608、插 283 buffers in 304 nets、动 706 条网
   （cells 22,048 -> 22,331），随后 DRT 连报
   “1 pin not visited #guides = 9 / 8”与“checkConnectivity break”中断。

2) 即使 resizer 不动单元（affected = 0），重新布这 12 条网时 DRT 仍然在
   某几条网的 pin 上失败（net _03524_ / pin _16242_/B1 等）。这不是驱动能力
   问题，是这些 pin 在已收敛的布线里接入点被邻居占用，局部重布拿不到可用
   接入点。

所以 60 个残余需要的不是再加一轮 ECO，而是结构级改动：对这几条高扇出网
在 RTL 层做扇出复制/重构，或者接受“约束比 PDK 更严”这一口径下的部分残留。

--------------------------------------------------------------------------
六、这次没有做的
--------------------------------------------------------------------------
- 新库（eco_it2）上还没有重跑六项物理复核：功耗、iRdrop、天线、密度、
  DRC（仅 DRT 内部 0 违例）、LVS。也没有从新 DEF 出 GDS、没有跑 XOR。
- 因此对外页面与 PDF 的数字仍是 tapeout 版那套，没有替换成“60”。
- filler 在局部 ECO 时尚未回填，最终交付前需要补 fill 再复核。

八、ECO 版库（eco_it2）上的六项物理复核：已复现的项目
--------------------------------------------------------------------------
复核对象是第 2 轮局部 ECO 的库 /tmp/eco/eco_it2.odb（Slowest 角 slew 60，
cap 126.3 pF，setup +1.31，hold +1.33）。标定口径与 tapeout 版逐项对齐。

1) 功耗（tt 1.80 V 25 摄氏度，寄生 it2nom.spef）
   活动率 0.10 -> 9.57e-03 W   (Internal 7.18e-03 / Switching 2.39e-03 /
                                Leakage 9.08e-08；Seq 52.5% / Comb 4.0% / Clock 43.6%)
   活动率 0.01 -> 9.16e-03 W
   活动率 0.50 -> 1.07e-02 W
   与 tapeout 版 9.57 / 9.16 / 10.7 mW 逐值一致。

2) iRdrop（PDNSim，VPWR 1.80 V / VGND 0 V）
   VPWR 最差 1.09e-03 V、平均 1.13e-04 V；VGND 最差 1.08e-03 V、平均 1.11e-04 V；
   两网 PSM-0040 全连通。与 tapeout 版 1.09 mV / 1.08 mV 逐值一致。

3) 寄生（nom 角）it2nom.spef 18,554,283 B，131,428 wires / 15,620 nets /
   78,745 rsegs / 168,895 ccs。

4) GDS 与 filler
   filler 回填后 eco_it2_fill.def 含 35,334 个 fill 单元（tapeout 版 25,656）。
   从 DEF 出 GDS 试了两版，结论不同，记录如下：
   - eco_it2.gds 42,779,502 B（先 gds read 再 lef read）：版图侧提取出
     16,217 个器件 / 17,044 个网，与网表侧 15,983 / 15,828 对不上，
     且 VPWR 引脚只连到 30,722 处（另有 2,382 处悬空）——单元视图在这一版里
     是不完整的，不能用于 LVS。
   - eco_it2b.gds 45,931,716 B（先 lef read + def read，再 gds read 单元库）：
     版图侧 15,983 个器件，与网表侧 15,983 完全相同；VPWR 与 VGND 各连
     33,083 处，两侧衬底已经接上。这一版才是可用于比对的那一版。

5) LVS（netgen + sky130A_setup.tcl，两侧同为 94 端口 / 16,552 实例 / 144 个子单元）
   器件数已逐值相等（15,983 | 15,983），单元引脚集等价，但网数
   15,931 | 15,828 仍差 103，报告判为 “Top level cell failed pin matching”，
   尚未达到 uniquely match。残余差异集中在 131 条只有 1 个连接的版图网
   （形如 _16239_/A，即引脚上没有接上几何），以及顶层 VGND/VPWR 两个
   电源引脚在两侧拓扑完全对称时无法定名。
   同一套脚本对 tapeout 版 GDS 是能跑到 Circuits match uniquely 的，
   所以这不是脚本退化，而是这份 GDS 的引脚接入没有被提取器认到。

6) 仍未跑：天线、密度、signoff DRC、XOR。

工具侧的限制也一并记下：chroot 内 klayout 0.29.1 只能打印版本，
任何 -r 脚本执行都在 tlFileUtils.cc:979 处崩，所以官方那条
DEF+LEF -> KLayout stream_out -> GDS -> XOR 的路径当前不可用；
magic 出 GDS 这条路能出图，但上面第 4 条已经说明它对单元视图的取舍
会直接改变 LVS 结果，必须用 eco_it2b.gds 这一版。

因此对外页面与 PDF 的数字仍然没有替换：六项复核还没跑完，
不能拿半套结果去改“数字自证”的账。

九、订正与补齐（2026-11-14 追加；第八节原文保留，不做覆盖）
--------------------------------------------------------------------------
第八节写于密度 / DRC / XOR / 官方出图路线跑出来之前，其中三处判断已被
实测推翻，另有三项补上了数值，一项确认仍无结果。逐条如下。

1) 721 条 implant DRC 的归因订正
   第八节把「先 gds read 再 lef read」当成 721 条违例的成因，这个归因不成立。
   本轮实测：手写脚本 mag_gds_it2b.tcl（gds read -> lef -> def）出的
   eco_it2b.gds 45,931,716 B，跑 sky130A_mr.drc 得 721 条
   （hvtp.2 443 / psd.2 96 / psd.1 79 / nsd.1 49 / nsd.2 22 / hvtp.1 13 /
     npc.2 13 / li.6 6）；
   而同一个脚本跑 tapeout 版官方 GDS 是 0 条。
   改用 OpenLane 官方 mag_gds.tcl（read_pdk_gds -> gds noduplicates true ->
   load (NEWCELL) -> read_tech_lef -> read_def -> load 设计 ->
   cif *hier write disable -> gds nodatestamp yes），环境变量：
   SCRIPTS_DIR / DESIGN_NAME / CELL_GDS / CELL_LEFS / TECH_LEF / CURRENT_DEF /
   MAGIC_MACRO_STD_CELL_SOURCE=PDK / MAGIC_ZEROIZE_ORIGIN=0 /
   DIE_AREA="0 0 640 640" / STEP_DIR / SAVE_MAG_GDS /
   MAGIC_DISABLE_CIF_INFO=1 / MAGIC_GDS_POLYGON_SUBCELLS=1，
   得到 eco_it2c.gds 41,419,812 B，DRC 同样是 6 条 li.6。
   因此：出图顺序不是 LVS 差异的原因；第八节第 4 条里
   「eco_it2b.gds 才是可用于比对的那一版」需要按本条修正为
   「三版 GDS 对 LVS 给出的数字完全相同」（见第 6 条）。

2) KLayout 这条路径恢复可用（第八节第 6 条的工具限制已作废）
   真因不是 chroot 的 /proc，而是 chroot 默认 PATH 里没有 coreutils，
   klayout 启动时要 mkdir / ln 一个 /proc/<pid>/exe 符号链接，缺 coreutils
   就地崩。补上 coreutils 的 PATH 后 klayout 0.29.1 正常跑脚本：
   DEF -> GDS 得 eco_it2b_kl.gds 19,466,372 B
   （日志：def read cells=159 / missing gds cells: [] count 0 / wrote）。
   另外官方 stream_out.py 不能用 "klayout -r stream_out.py -- ..." 传参
   （它用 click 解析，报 ERROR: Unknown option: --），改成 python3 + pya
   直调即可（脚本 /tmp/kl/so_it2b.py，PYTHONPATH 指向 klayout-pymod）。

3) 密度（eco_it2b.gds，klayout check_density，5.450 s，items 为空 = 0 违例）
   li1 0.7424973667602539   m1 0.7231207860107423
   m2  0.9032449227905274  m3 0.922803524597168
   m4  0.9481101244506835  m5 0.97229390625
   对照 tapeout 版 0.4991372 / 0.7232361 / 0.9033210 / 0.9223075 /
   0.9478303 / 0.9715806：六值均不低于 tapeout，且无密度违例。

4) signoff DRC（sky130A_mr.drc）四组实测
   eco_it2b.gds（手写 magic）  721 条（见第 1 条逐类计数）
   eco_it2b_kl.gds（klayout）    6 条，全 li.6
   eco_it2c.gds（官方 mag_gds）  6 条，全 li.6
   tapeout 官方 GDS              0 条
   6 条 li.6 的位置（各为 0.17 x 0.17 um 的 li1 小方块，即 li1 尺寸临界）：
   (319.845,376.465)-(320.015,376.635)
   (340.085,510.085)-(340.255,510.255)
   (415.525,430.185)-(415.695,430.355)
   (415.525,430.865)-(415.695,431.035)
   (320.305,377.145)-(320.475,377.315)
   (161.605,248.965)-(161.775,249.135)
   两套彼此独立的出图工具（magic / klayout）给出完全相同的 6 条，
   说明这是 DEF 里 6 处 li1 几何临界，而不是某一版生成器的缺陷。
   结论：这一版 DRC 不是 0 条，是 6 条 li.6。

5) XOR（klayout XOR：klayout 出图 vs 手写 magic 出图，43 层）
   rc 0，TOTAL_DIFF = 94,607。逐层非零：
   236/0 = 16,727    67/16 = 2,576    78/44 = 231    81/14 = 1
   81/4  = 4         93/44 = 5,884    94/20 = 7,489  95/20 = 61,695
   其余 35 层为 0。注意：这些层号在 sky130A.map 里没有对应条目
   （map 内唯一的 23x 条目是 DIEAREA ALL 235 4，与 236/0 不同），
   层语义未确认。因此这个 XOR 只能作为「两版 GDS 不等价」的证据，
   不能反过来当作「版图一致」的证据使用。

6) LVS：三版 GDS 给出的数字完全相同（含官方 mag_gds 版）
   eco_it2b.gds / eco_it2b_kl.gds / eco_it2c.gds 三次跑，
   结果一致：Number of devices 15,983 | 15,983（相等）
             Number of nets    15,931 | 15,828（差 103）
             Cell pin lists altered to match / Device classes equivalent
             最终 Final result: Top level cell failed pin matching
   对照实验：网表换 eco_it2nl_nofill.v 仍是 15,931 | 15,828；
   netgen 加 -flatten 数字一字不变。
   即 103 条网差与 fill、层级命名、GDS 生成方式都无关。

7) 天线：三次尝试均未出结果，判为工具路径受阻
   三次都停在 magic 的 "Processing sha256_axil" 之后：
   (a) 手写 dereference 版（lef -> def -> gds read -> load -dereference）；
   (b) 完整复刻 LVS 里已跑通的提取配方，末尾换成 antennacheck；
   (c) 同 (b) 但去掉 extract unique。
   进程状态：sleeping，wchan = request_wait_answer（阻塞在 openat），
   CPU 约 2%，RSS 185-318 MB，工作目录始终无 .ext 落盘，20-40 分钟无进展。
   对照事实：同一台机、同一 magic 版本，LVS 里那一步提取能在约 13-22 分钟
   正常产出 layout.ext.spice。所以这不是「慢」，是这条脚本组合在本设计上
   卡住。天线这项在 ECO 库上记作「未复核」，不给数值。

8) 与第八节一致的部分（不再重复展开）
   功耗 9.57e-03 / 9.16e-03 / 1.07e-02 W（act 0.10 / 0.01 / 0.50）；
   iRdrop VPWR 最差 1.09 mV、VGND 最差 1.08 mV；filler 35,334；
   it2nom.spef 18,554,283 B（131,428 wires / 15,620 nets）。

九节结论：
   ECO 版的六项复核里，功耗 / iRdrop / 密度有数且与 tapeout 对齐，
   XOR 有数但只能证明两版不等价，DRC 从 0 条变成 6 条 li.6，
   LVS 从 uniquely match 退成 15,931 | 15,828，
   天线没有结果。按这个状态，① 项不能写成「六项复核通过」，
   页面与 PDF 的数字继续保持 tapeout 版口径，不替换。

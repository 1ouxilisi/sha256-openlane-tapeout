LVS 口径更正与三项对照实验
====================================================
生成时间：2026-11-07
对应提交：上一版 numbers.html 第三节 "1,795 行实例缺单元名"
本文件作用：更正上一版的错误结论，并记录本轮三项可以独立复现的实验。

----------------------------------------------------
一、更正：1,795 行不是"缺单元名"，是 SPICE 折行
----------------------------------------------------
上一版写"顶网表 33,984 行实例里，1,795 行（5.3%）最后一个 token 是网名而不是
单元名"。本轮重新检查，这个结论是错的。

判定方式：上一版把每一行当独立语句，用"该行末 token 是否落在文件内 154 个
.subckt 名集合"来判断。Magic 的 exttospice 输出遵循标准 SPICE 续行语法，
超长实例行会在下一行以 "+" 开头续写，单元名就在续行上。

实测数据（在 sha256_axil.ext.spice 的顶层 subckt 体内统计）：
  - 全文件以 "+" 开头的行：1,813
  - 顶层 subckt 体内以 "+" 开头的行：1,813（其余在单元定义体内，0 行）
  - 顶层 X 实例行：33,984
  - 其中下一行以 "+" 开头的：1,795
  - 把续行拼接后重新判断：33,984 / 33,984 全部带单元名，缺名 0 行

原文样例（相邻两行）：
  X_20693_ VGND VPWR VPWR VGND clknet_leaf_41_clk net790 net193 u_core.W\[3\]\[23\]
  + sky130_fd_sc_hd__dfrtp_1

所以：上一版"1,795 行缺单元名"这个卡点定位是假卡点，必须撤回。
由此推出的"两边实例结构从这一层就不相等"也不能再用。

----------------------------------------------------
二、实验一：版图网表自比，0 个问题
----------------------------------------------------
做法：把 sha256_axil.ext.spice 复制一份为 ext_b.spice（内容完全相同，只是文件名
不同，否则 netgen 认为"Both cells are in the same netlist: Cannot compare"），
两边都比 sha256_axil。

命令：
  netgen -batch lvs "sha256_axil.ext.spice sha256_axil" \
                  "ext_b.spice sha256_axil" \
                  /pdk/sky130A/libs.tech/netgen/sky130A_setup.tcl self.out

结果：
  - 出现 "(no matching pin)" 的行数：0
  - "Cell pin lists are equivalent."
  - "Device classes sha256_axil and sha256_axil are equivalent."
  - "Final result: Circuits match uniquely."

含义：netgen 能完整读懂这份 2.78 MB 的版图提取网表，98 个顶层端口一个不少地
读进来并全部对上。所以失败不在"读取"或"折行"，而在两个网表的配对本身。

补充实验（排除端口表被截断）：
  - 单行 1,295 字符 / 78 端口的构造网表：全对（Circuits match uniquely）
  - 同样 78 端口但按 "+" 折成 16 行：也全对
  → 长行与折行都不是瓶颈，上一版怀疑的方向不成立。

----------------------------------------------------
三、实验二：另一侧的网表是不是乱造的
----------------------------------------------------
把 pnr5.spice（由 nl.v 转换而来）逐实例逐脚与 nl.v 原文核对：
  - 比对口径：只比 nl.v 中显式写出的信号脚（电源 VGND/VPWR/VPB/VNB 在 nl.v 里
    不出现，由转换器按全局网补上，不参与比对）
  - 逐脚一致：15,381 个实例
  - 不一致：206 个（都是 nl.v 中该引脚不存在的特殊实例，集中在时钟负载与常量
    类单元，例如 clkload0 的 X 脚）
  - 不参与比对：31,499 个实例只有电源脚（fill / decap / tap），无信号脚可比
  - 单元名全部对上：0 个单元名不一致

含义：另一侧网表不是乱造的，转换器在 15,381 个实例上是忠实的。

----------------------------------------------------
四、结论（这是本轮能站得住的部分）
----------------------------------------------------
1. "1,795 行缺单元名"撤回。它是 SPICE 折行，拼接后 33,984/33,984 都有单元名。
2. 版图网表自比 0 问题，98 个端口全读全对 → netgen 侧无障碍。
3. 另一侧网表 15,381 个实例逐脚忠实 → 不是转换器乱写。
4. 因此 47 个端口 (no matching pin) + net 15,645 vs 15,647 是真实的版图与网表
   差异，范围已收窄到：时钟负载/常量类单元的特殊连接，以及两侧网名集合的
   212 / 11 处不对称。不是名字问题，不是折行问题，不是格式问题。
5. 仍未通过 LVS。上面四条不构成"通过"，只是把"为什么没过"从假因收回真因。

----------------------------------------------------
五、没做的
----------------------------------------------------
- 没有把这 47 个端口逐个追到具体的驱动/负载单元（需要按单元逐个展开网名集合，
  工作量大于本轮）。
- 没有为 206 个例外实例补出正确连接（clkload0 的 X 脚在 nl.v 里不存在，需要从
  DEF/ODB 取实际连接）。
- 没有做第二引擎的独立等效裁决（KLayout NetlistComparer 对这份数据会给误报通过，
  见 lvs_instance_audit.txt 第五节，仍不采用）。

六、复现命令
----------------------------------------------------
自比：
  cd /home/user/openlane-rootfs/tmp/lvs
  cp sha256_axil.ext.spice ext_b.spice
  sudo chroot /home/user/openlane-rootfs \
    /nix/store/306znyj77fv49kwnkpxmb0j2znqpa8bj-bash-5.2p26/bin/bash -c \
    'export PATH=/nix/store/b9kirpfkif1852bcy64f96np93xjalsi-netgen/bin:$PATH; \
     export PDK_ROOT=/pdk PDK_PATH=/pdk/sky130A; cd /tmp/lvs && \
     netgen -batch lvs "sha256_axil.ext.spice sha256_axil" \
       "ext_b.spice sha256_axil" /pdk/sky130A/libs.tech/netgen/sky130A_setup.tcl self.out'

折行判定：
  读顶层 subckt 体；若某 X 行下一行以 "+" 开头则拼接后再取末 token；
  统计末 token 落在 .subckt 名集合中的行数（本轮 33,984/33,984）。

比折行更容易踩的坑：直接按行切分会把 1,795 行误判成"缺单元名"（上一版即如此）。

六、DRV：两套口径分开写，缺一条就不诚实
(1) PDK 库自身口径：三个 liberty 的 default_max_transition 都是 1.5000000000 ns；库里不设 default_max_fanout，也不设 default_max_capacitance。
    三 corner 结果：max slew 0 / max capacitance 0；max fanout 这一格写 0 的含义是「没有上限可违」，不等于扇出干净。
    即：按 PDK 自己的规则，这一版设计规则是干净的。
(2) 项目自己加严的口径（set_max_transition 0.75、set_max_fanout 10）：
    Fastest  slew 0   / fanout 61 / cap 0
    Typical  slew 8   / fanout 61 / cap 0
    Slowest  slew 275 / fanout 61 / cap 0
    最大 slew 1.25 ns（限 0.75，超 0.50）。
    只报 275 会让人以为是硅上的硬伤；只报 0 等于把口径偷偷换成宽松那一档。所以两行都留。

结论：21 条新违例里，逻辑负载全部 ≤10（最大正好 10）。把物理专用的天线二极管引脚从扇出计数里去掉，21 条全部回到限值内，扇出违例回到基线那 40 条。也就是说天线修复没有把任何一条网真的压过逻辑扇出上限，越线的全是二极管自己那 1–10 个引脚（net9 一条网上挂了 10 个二极管）。
但这只是口径解释，不能当「已清」：OpenSTA 的 report_check_types 默认把二极管引脚算进 fanout，本文件没有改这个判据，也没有为了好看去改 SDC。

九、口径自检：旧三份 mcsta 日志为什么「grep 不到 read_spef」却仍是带寄生的
io.tcl 的 read_spefs（第 306 行）读 $CURRENT_SPEF，然后 foreach 循环写进全部三个 corner，全程不打印。所以日志里 grep 不到 read_spef 不等于没读寄生。
代价是：每次 run 只有一个角的 SPEF 被复制到三个角，三次 run 之间数字因此不同（Slowest setup 0.9853 / 0.5077 / 0.7417）。
正确读法是每个角取对应那次 run：Fastest 取 min 那次 11.9755、Typical 取 nom 那次 9.1864、Slowest 取 max 那次 0.5077。
本次单进程逐角配对的结果与这个「分取」逐位相同（基线 11.9755 / 9.1864 / 0.5077）——说明两种读法等价，旧页面的数没有错；错的是「一份 run 就能给三个角」这个隐含前提，这一版才第一次真正成对读。

十一、它不证明什么
- 没跑 IR-drop，这一版仍没有电压降结论。
- 没取功耗：report_power 有输出但没解析，不与旧版数字混用。
- 没做 ECO：275 / 61 是实测，不是「已修」。要清得插 buffer 或改时钟树，会改版图，前面六项物理结论需重跑。
- 不是硅结果：三个角都是库模型 + 提取寄生。
- fill 与二极管在 STA 里当真实负载，与版图一致；但 STA 用的是连接关系 + SPEF，不是 DRC/LVS 的几何判据。

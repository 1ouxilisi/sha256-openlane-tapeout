LVS 抽取复现性复核（2026-11-10）

一句话：同一份 GDS 两次独立抽取，网表逐字节相同，netgen 两次都给出 Circuits match uniquely。
因此"换会话重抽就对不上"这条说法撤回；真正的问题在调用方式，不在版图、不在引擎。

二、版图侧已无差别（复核结论，不是推断）
====================================================================

1. 二进制
   eco_it2f.gds 与 eco_it2z.gds 均为 41,618,404 B。
   cmp -l 差异 450 字节，全部落在记录头：偏移 30 / 94 / 2,274 / 4,936 / 6,220 ...
   按 GDS 记录流解析，命中的记录类型是 0x102（BGNLIB，len 28）与一串 0x502（BGNSTR，len 28）。
   即差异只有 version 字节与两组 timestamp，没有几何差异。

2. 标签
   顶层 datatype == 5 的 text：两侧各 112 个。
   (layer,string) 分组后坐标逐个比对，total diff labels 0。
   分布 (72,5)=8 / (71,5)=8 / (70,5)=79 / (69,5)=17，VGND x8 + VPWR x8 两侧一致。

3. 形状
   43 层共 562,105 个形状，两侧一致。

结论：同一份 DEF 出来的两份 GDS，几何与标签完全相同。

====================================================================
三、早前"时并时不并"的读数是怎么来的
====================================================================

病根在 ext2spice 的第二参数，不在版图。

magic 的写法是 ext2spice -o <输出文件> <ext 名>。当 <ext 名> 指向一个不存在的目录时，
magic 不打 error、不写文件，直接回落到当前目录里已有的 sha256_axil.ext
—— 也就是上一次抽取留下的缓存。

本轮实测：
  ext_it2f_re.tcl 里写的是 ext2spice -o /tmp/n52/layout_it2f_re.spice sha256_axil_re.ext
  跑完打出 SPICE_DONE，日志里 Total of 2 warnings，但目标文件不存在。
把第二参数去掉、只写 ext2spice -o /tmp/n52/layout_it2f_re.spice，另起一个会话跑，
1,686,735 B 正常落盘，md5 与第一次完全相同。

由此可以解释 18:32 / 18:39 / 18:45 那三个"97 端口、无 VGND"的文件：
  layout_it2z.spice = layout_it2h.spice = layout_it2c2.spice
  各 1,667,321 B，md5 全为 c03acf6a791bf1052b35f3f889a5014a
三份文件彼此逐字节相同，正是因为它们同源 —— 同一份缓存被三次读出，而不是三次独立抽取。

所以：早前记的"同一份 DEF / GDS 换会话重抽 → VNB 井网并进 VPWR、15,981 vs 15,983"
这条结论，撤回。它测到的是缓存，不是版图。

--- 7.3 "magic 卡住"的真病根：cwd 里没有标准单元的 .ext 缓存
先撤回一条旧判断：反复 kill 的那几次并不是挂死，而是在极慢推进 ——
CPU TIME 6s -> 11s 持续上涨、RSS 恒 420 MB、无子进程、/proc/<pid>/io 的 rchar
停在 44,246,538、vmstat r=0，日志停在 "Processing sha256_axil" 之后不是死锁，
是前面那些 cell 还在等。
病根：magic 顶层 extract 要逐个 cell 出 .ext，cwd 里找不到就现场重抽，
148 个标准单元 × 每次几秒到几十秒 = 十几分钟到假死量级。
三组对照（均在空目录里起跑）：
  t8  只抽单个 sky130_fd_sc_hd__inv_1            -> 秒级完成
  t9  连续抽 5 个 cell                            -> 全部完成（T9_DONE）
  t6  先把 148 个 .ext 拷进 cwd、删掉 sha256_axil.ext 强制重抽顶层
      -> 完整跑完（Total of 2 warnings. / ext2spice finished. / T6_DONE）
         sha256_axil.ext 19,823,266 B
         layout_t6.spice 1,686,735 B md5 09183c364b9f5e749c05cfb23a8e3333（与历史通过版逐字节相同）
  t7  把 148 个 .ext 放另一个目录、两次 addpath 指过去、cwd 仍为空 -> 照样停住
结论：修法是 cp 进 cwd，addpath 不能替代。
（附带：t6 的 .ext md5 97846eb5… 与 /tmp/n52 的 31cd200c… 不同，但导出的 spice
 完全一致 —— .ext 的中间态不稳定，判据只认 spice。）

八、差额拆开看：2 个器件 / 29 条网 / 顶层 VGND 并进 VPWR（2026-11-11 追加）

先更正一处说法：「eco_it2f.gds 是无二极管版」是错的，撤回。
  直接读两份 GDS 的顶层实例（klayout.db，不经过网表）：
    eco_it2f.gds  顶层实例 57,382   diode_2 327   fill_8 15,122 / fill_4 5,710

8.1 那 2 个器件

  参考侧多出的 20,832 个 fill 是 fill 单元无器件、版图抽取不收，压平后不影响器件数。

8.4 硬事实：这一版抽出的网表里 VGND 整个并进了 VPWR
  顶层实例引脚按网名计数（拼 "+" 续行后按 token 计）：
    layout_f4.spice  inst 16,552  VGND 33,104  VPWR 33,104  VNB 0  VPB 0  （prep_lay 后 94 脚）
    layout_g5.spice  inst 16,572  VGND      0  VPWR 66,562  VNB 0  VPB 0  （prep_lay 后 93 脚）
  通过版每颗单元 2 个 VGND + 2 个 VPWR；it2g 版四个电源脚全记在 VPWR 上。
  93 vs 94 端口只是表象，网表里 VGND 这条网已经不存在。

8.5 标签层面已证伪「标签丢了」

  bbox dbu 0.001，top cell 均 sha256_axil。
  → 标签没丢、没改名；端口消失发生在抽取 / 命名层。
  it2g 上两个标签点所在的 met1(68/20) 多边形：
    VGND 点 (319930,490370) → bbox (317945,490320;320090,490905)
    VPWR 点 (319930,487070) → bbox (5520,486640;634340,487120)
    两点不在同一多边形，不是「同名标签压在一条线上」这种简单短路。

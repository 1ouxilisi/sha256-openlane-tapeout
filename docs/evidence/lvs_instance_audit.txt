实例级对账 —— 47,087 / 33,984 / 15,588 这三个数字的关系
============================================================
生成时间：2026-11-07
现场：/home/user/openlane-rootfs/tmp/lvs/
输入：sha256_axil.ext.spice（Magic 提取，2,785,763 B）
      sha256_axil.pnr5.spice（PnR 网表转出，3,452,700 B）
      results/routing/sha256_axil.nl.v（3,347,552 B）

这份文件解决的问题：作品集里同时出现 47,087、33,984、15,593 三个数，
读者看不出它们是什么关系。这一版把它们拆到能对账。

--------------------------------------------------
一、三个数字各自是什么
--------------------------------------------------
47,087 = metrics.csv 的 TotalCells，也是 PnR 实际放置的单元总数。
         sha256_axil.nl.v 里正好 47,087 行实例，
         其中 31,499 行是空引脚 `();`——fill、decap、tap 这类没有信号脚的单元，
         剩下 15,588 行是有引脚的实例。

33,984 = Magic 从 sha256_axil.gds 提取出的顶层实例数
         （sha256_axil.ext.spice 顶层 .subckt 体内 X 开头的行数）。

15,593 = netgen 报的 "Circuit 1 contains 15593 devices"。

--------------------------------------------------
二、13,103 这个差被拆干净了
--------------------------------------------------
47,087 - 33,984 = 13,103

按单元类型逐类对照（两侧顶层实例）：
  sky130_fd_sc_hd__fill_1          版图 0   网表 5,667
  sky130_fd_sc_hd__fill_2          版图 0   网表 1,940
  sky130_fd_sc_hd__tapvpwrvgnd_1   版图 0   网表 5,496
  三项相加 = 5,667 + 1,940 + 5,496 = 13,103（正好相等）

其余 1,486 类单元单类差异有正有负（例如 dfrtp_1 版图 762 / 网表 1,576），
但非 fill / tap 类的净差合计 = 0。

结论：版图提取不产出 fill 与 tap（它们没有信号器件，提取时并入电源/衬底），
这就是 13,103 的全部来源，不是漏提了逻辑单元。

--------------------------------------------------
三、netgen 那个 15,593 是什么
--------------------------------------------------
15,588（nl.v 里有引脚的实例）+ 5 = 15,593。

所以 netgen 的 "devices" 是「有端口的实例数」，
既不是晶体管数，也不是 TotalCells。
之前挂着的「15,593 含义未确认」，到此有了答案。
差额 5 没有逐条对到，如实留着，不凑数。

--------------------------------------------------
四、连接级失配的真实来源：1,795 行没有单元名
--------------------------------------------------
sha256_axil.ext.spice 顶层 33,984 个 X 行里，有 1,795 行（5.3%）的
最后一个 token 是网名，而不是单元名。原文照抄两例：

  X_20693_ VGND VPWR VPWR VGND clknet_leaf_41_clk net790 net193 u_core.W[3][23]
  Xclkbuf_leaf_150_clk clknet_leaf_150_clk clknet_4_11__leaf_clk VPWR VGND VGND VPWR

（其中 1,682 行以 X_ 开头，113 行是 Xclkbuf_leaf_* 形式的时钟缓冲。）

这样的行，netgen 无法判定它是哪个单元，只能按未知单元处理，
于是内部网表与网表侧不同构——这才是
  Circuit 1 contains 15645 nets, Circuit 2 contains 15647 nets
和 47 行 (no matching pin) 的来源。

口径更正：上一版把原因写成「netgen 对这份手工转出 spice 的顶层端口识别」，
过于笼统。更准的说法是：版图提取网表里有 1,795 个实例没有写出单元名，
两边的实例结构从这一层就不相等。端口名写法、行长度、定义顺序、自动匹配
这四类变量此前已逐个排除，与本条不矛盾——它们排除的是「不是原因的东西」。

--------------------------------------------------
五、试过第二个引擎，它给了假通过
--------------------------------------------------
KLayout 的 Python 接口（klayout.db，0.29.1）里有 NetlistComparer，
可以直接读 SPICE 做比较，不依赖那个崩掉的 Ruby 引擎。实测：

  读入 ext_kly.spice / pnr5_kly.spice（把 2 行模型式电阻改成定值后才读得进）
  两侧顶层：pins 98 / 98，subckts 33,984 / 47,087，nets 15,649 / 15,655
  flatten() 展开后：两侧各剩 8 个器件，nets 84,182 / 84,188
  NetlistComparer.compare() 返回 True

8 个器件当然等价，这个 True 不能用，也不写进结论。

原因：KLayout 的 SPICE 读取器把「带参数器件」当成子电路，参数被编进电路名，
例如 SKY130_FD_PR__NFET_01V8(AD=0.10025,AS=0.1092,L=0.15,PD=0.985,PS=1.36,W=0.42)，
展开后并没有还原成器件。要它可用，得自己实现 NetlistSpiceReaderDelegate
定义器件抽取。这一版没做。

这一条留在证据里的理由：一个返回 True 的比较器，如果不看它到底比了多少东西，
就会变成「假的通过」——那比没有第二个引擎更危险。

--------------------------------------------------
六、结论
--------------------------------------------------
1. 47,087（放置单元）= 15,588（有引脚实例）+ 31,499（空引脚 fill/decap/tap）。
2. 33,984（版图提取实例）= 47,087 - 13,103（fill_1 + fill_2 + tapvpwrvgnd_1）。
3. netgen 的 15,593 约等于 15,588 + 5，含义是「有端口的实例数」。
4. 连接级失配定位到 1,795 行缺单元名的实例；器件级 15,593 = 15,593 仍成立。
5. 第二引擎尝试失败，且出现假通过，不采用。

--------------------------------------------------
七、没做的
--------------------------------------------------
- 没有把这 1,795 行补上单元名（需要从 GDS 的 cell 边界 + DEF 重新映射，
  或改用 Magic 的层次化提取参数）。
- 没有第二引擎的等效裁决。
- 差额 5 没有逐条对到。

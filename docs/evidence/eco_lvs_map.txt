ECO 版 LVS 的一次映射探针：名字不是死路，多出来的 103 条网才是
================================================================

一句话：这一节不解 LVS，只把「netgen 为什么卡」从一句猜测换成一串可复算的数——
16,552 个顶层实例两侧同名同脚数，一条不差；按端口名对齐后，15,931 条版图网
逐一落到 15,828 条网表网里的一个，零冲突；反方向却有 68 个网名各收到两到八条
版图网，合计多出 103 条。名字映射这条路走得通，卡住的是这 103 条。

----------------------------------------------------------------
一、起点：上一轮已经把「名字对不上」定性了
----------------------------------------------------------------

`tmp/lvs_it2c/` 那份 lvs.out（653,907 B，8,362 行）停在
`Top level cell failed pin matching`，`lvs_np2.json` 记 badnets 119 /
badelements 36 / nets [15931, 15828]。上一轮的定性是：版图侧网表来自 GDS 提取，
magic 在 MAGIC_DEF_LABELS=0 下只能按驱动脚自造网名（`_10608_/X`），网表侧则是
真实名（`_06035_`），两边名字层面无从对应；顶层还有 119 个结构完全同构的网
（一个 clkbuf 驱动一个 a22o 的 A2，一驱一载），netgen 建不起映射，全记成 badnet。

这一轮不重跑 netgen，只做一件事：把「名字能不能从结构推出来」当场算一遍。
如果能，那 LVS 的失败就不该再解释成「没名字所以判不了」；剩下的 103 条网差
才是真问题。

----------------------------------------------------------------
二、做法：两版对齐，第一版按位置对齐会把电源脚错配
----------------------------------------------------------------

输入两份网表，都是 it2c 那一轮的产物：

  /tmp/lvs_it2c/lay.spice   1,684,479 B   版图侧，prep_lay.py 清洗后（掉 4 个悬空端口）
  /tmp/lvs_it2c/net.spice   2,872,118 B   网表侧，nl2spice.py 把 VNB/VPB 并进电源后

第一版按「脚的位置」对齐（t[1:-1] 直接 zip）。结果是灾难：单一个版图网 `VPWR`
就映射到了两百多个网表网名——因为同一颗标准单元在两份文件里的 `.subckt`
端口顺序不同（`a22o_1 = VPWR VGND VPB VNB B1 A1 A2 X B2` 与另一份的排列不保证
一致），按位置对齐等于把电源脚、体端脚、数据脚整体错位。这一版作废。

第二版按「端口名」对齐：先从每份文件自己的 `.subckt` 声明里读出每个单元的端口
顺序表，再把实例脚按名字配回去，然后按端口名逐脚取两侧网名。这个才是有意义的
对齐方式，也是任何 LVS 工具在没有标签时唯一站得住的入口。

脚本 `/tmp/n52/lvs_map.py`，输出 `/tmp/n52/lvs_map.out` 与
`/tmp/n52/lvs_map_multi.txt`（后者是那 68 个网名的逐条清单）。

----------------------------------------------------------------
三、三个数
----------------------------------------------------------------

（数一）顶层实例：版图侧 16,552 个，网表侧 37,384 个。
  交集 16,552，只在版图侧 0 个，只在网表侧 20,832 个，且这 20,832 个前缀全是
  `FILLER_`（`FILLER_0_162_1032`、`FILLER_0_120_654` …）——prep_lay.py 清洗时
  把 filler / decap / tap 那一批删掉了，网表侧没删。也就是说版图侧每一个实例
  在网表侧都能找到同名同脚数的对应，缺失为零。

（数二）端口脚数：16,552 个共有实例里，脚数不匹配 0 个。

（数三）网：版图侧 15,931 条，网表侧 15,828 条。
  正向（版图网 → 网表网）：15,931 条全部有落点，**落在多个网表网的 0 条**。
  反向（网表网名 ← 版图网）：**68 个网名各收到 2 到 8 条版图网**，
  多出来的版图网合计 **103 条** —— 与 15,931 − 15,828 的差逐条对上。
  这 68 个的分裂宽度：2 条 46 个、3 条 17 个、5/7/8 条各 1 个、4 条 2 个。

----------------------------------------------------------------
四、抽一条看原文：DEF 说是同一网，版图提取给了两条
----------------------------------------------------------------

抽 `_07117_`。DEF 原文（`tmp/eco/eco_it2_fill.def`，NETS 段第 5,528,857 字节起）：

  - _07117_ ( _12670_ C1 ) ( _12585_ A1 ) ( _12462_ C_N ) ( _12420_ A1 ) ( _12333_ A1 ) ( _12330_ Y ) + USE SIGNAL

一个驱动（`_12330_/Y`）+ 五个负载。版图侧却被拆成 `_12330_/Y` 与 `_12670_/C1`
两条网（该网名收到 2 条版图网）。其余分裂的驱动单元类型分布（按版图侧自造名的
驱动实例统计）：clkbuf_1 29、nand2_1 17、nor2_1 8、xnor2_1 7、a22oi_4 6、
buf_4 6、clkbuf_4 6、inv_2 6、a21oi_4 6、or2_1 5 …… 都是普通单元，
不是某个特殊 cell 的问题。

----------------------------------------------------------------
五、这说明了什么，没说明什么
----------------------------------------------------------------

说明（可以当结论写进对外材料的）：
  1. 「因为 magic 没标签、名字对不上，所以 LVS 判不了」这个说法不成立。名字可以
     从实例-端口结构唯一地推出来，正向映射零冲突。
  2. 15,931 与 15,828 之间那 103 条差，有了精确的形状：不是 103 条孤立的多余网，
     而是 68 条网表网在版图侧被拆成了两截以上。
  3. 因此 LVS 的下一步不是再去想办法补标签，而是把这 103 条定性。

没说明（不能写成结论的）：
  1. 没有证明版图有 103 处开路。拆分可能来自 magic 提取时未合并（例如跨单元的
     连接只走 met1 到 li1 的 licon，或某类形状被判成非电气类型），也可能是真开路。
     两种都还没有证据把它排除。
  2. 没有证明两侧器件级等价。器件数 15,983 | 15,983 是上一轮 lvs.out 的数，
     本轮没有重新提取，也没有重跑 netgen。
  3. 因此本节的定位是「把 LVS 的失败点收敛成一条可查的线」，不是「LVS 有解了」。

下一步有两条，都不需要再猜：
  A. 拿一条已经 PASS 过的版图-网表对，跑同一个探针，看它是否也出现同样量级的拆分
     —— 若也出现，说明是这条提取链的固有口径；若不出现，说明这 103 条是本轮新长出来的。
     **这条已经跑了，见第七节，结果是 0 条。**
  B. 抽 3 条（`_07117_` 起）在 magic 里逐点看：两条网各自的形状、中间是否有
     licon/mcon、间距多少。一条定性就够定性整类。**这条还没跑。**

----------------------------------------------------------------
七、正对照：已经 PASS 的那一版，同一个探针是 0 条
----------------------------------------------------------------

上一节列的路 A 直接可跑，不需要新提一遍版图：`/home/user/lvspkg/work_full/` 里
留着 tapeout 版的提取产物（那一版 netgen 判 `Circuits match uniquely`，
lvs.out 第 4,200 行原文；34,182 实例、36,256 器件）。

  lay.spice   2,768,173 B   版图侧（同一份 prep_lay.py 清洗）
  net.spice   2,708,330 B   网表侧（同一份 nl2spice.py 生成）

把 `/tmp/n52/lvs_map.py` 的两个输入换成这一对，脚本其余部分一字不动
（`/tmp/n52/lvs_map_tapeout.py`），结果：

  top insts layout=34182 net=34182
  common=34182 only_net=0 only_layout=0        （注意：0，且没有 FILLER 前缀）
  pin-count mismatch=0
  layout nets=15795 net nets=15795
  layout_net->multi=0    netname<-multi=0  extra_layout_nets=0

也就是说：同一套「magic 提 GDS → prep_lay 清洗 → nl2spice → 按端口名对齐」的链，
在一个 LVS 真正通过的版对上，15795 条版图网与 15795 条网表网一一对应，
分裂 0 条、多出来的网 0 条。

结论因此可以往前推一格（但仍不到「LVS 有解」）：
  1. 那 103 条不是 magic 提取链的固有口径，也不是「没标签」的必然结果 ——
     同样的入口在另一版上分裂为零。
  2. 所以它是**这一版特有的**：要么 ECO 这版 GDS 里有真断路，要么这一版
     DEF→GDS / 网表两条生成路里有一条把某类连接办丢了。二选一，范围已经很小。
  3. 仍然没有证明是哪一边。下一刀是第五节的路 B：挑 1 至 3 条，在 magic 里
     看两截之间到底有没有 licon/mcon、间距多少。这一步做完，"是形状没接上
     还是提取没合并"就能定下来。

复现（对照侧）：

  python3 /home/user/openlane-rootfs/tmp/n52/lvs_map_tapeout.py
  # 期望 layout nets=15795 net nets=15795 / multi 两行都是 0

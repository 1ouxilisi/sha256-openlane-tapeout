七代演进：每代只解决一个问题

不是调参刷数字。每一代的起点都是上一代暴露的一个具体缺陷。

v1 · 先把链路跑通tapeout6

单块组合逻辑、773 个并行 IO、不做流水线。38.58 MHz / 0.64 mm² / 利用率 20.99%，布线 0 违例。 用 RCX 真实寄生重签核后 WNS -15.92 ns —— 这一代的价值不是指标，是证明链路可行，以及暴露了三个短板：无流水线、IO 撑大 die、利用率只有两成。

v2 · 砍 IO，切两级流水tapeout9

顶层改成 32-bit 串行接口 + start/busy/done 握手，压缩核拆两级。中途 die 收到 550 直接拥塞 fatal， 最终靠 GRT_ALLOW_CONGESTION=1 + GRT_OVERFLOW_ITERS=200 让布线器收敛。 53.45 MHz（+38%）/ 0.49 mm²（-23%）/ 利用率 33.53%，收益最猛的一代。

v3 · 三级流水，撞见工艺墙tapeout10

压缩核再细分三级。58.17 MHz，只比 v2 高 9%。这里出现本项目最重要的认知转折： 单级组合逻辑已压到 6.64 ns，而签核关键路径是 17.19 ns —— 中间 10 ns 不是逻辑，是寄存器 CK-to-Q 加布线 RC。 瓶颈从"算得慢"变成"寄存器和连线本身慢"，再切流水没有意义。

v4 · 不再堆频率，改做面积tapeout12

die 从 700×700 收到 640×640，硬冲利用率。56.72 MHz / 0.4096 mm² / 40.65%，14 轮迭代把 DRC 从 16,283 收敛到 0。 代价是频率回落 1.45 MHz、WNS 从 -7.19 变 -7.63。这一代的意义是"做取舍"：知道何时该停、该换维度。

v5 · 把约束改对，让时序真正签核通过tapeout13

前面四代 flow_status 显示的 optimized WNS = 0 是 resizer 估算值，不是签核值。用 RCX 真实 SPEF 跑三 PVT corner， v1–v4 的 setup 余量全是负的。根因：config.tcl 里 CLOCK_PERIOD 从第一天就写着 10.0 ns（100 MHz 的愿望）， 而实际只到 56.72 MHz —— 约束比工艺能力激进一倍多。 不改 RTL、不动 die、不换策略，只把周期改成 26.0 ns 并给 resizer 加余量： 三 corner 全部转正（WNS 0.00 / TNS 0.00 / setup +5.00、+4.03、+3.12 / hold +0.43），功耗 6.31 mW。

v6 · 只压约束，测出余量还剩多少tapeout14

v5 余量是真富余还是取整碰巧？v6 把 v5 配置一字不动，只把周期从 26.0 改成 24.0 ns（41.67 MHz），干净的单变量对照。 三 corner 仍全为正：+3.08 / +2.12 / +1.25 ns，hold 稳定 +0.43，功耗 6.84 mW（+8.4%，频率 +8.3%，基本线性）。 把最紧角 1.25 ns 加回周期，得 22.75 ns ≈ 43.9 MHz —— 这就是这条 RTL 在 sky130A 上的定量边界。 但它只是"这条 RTL"的边界，v7 把它推掉了。

v7 · 换结构，而不是继续试探约束tapeout15 / tapeout16

前六代都在同一套 RTL 上压约束。v7 换掉消息调度：W 从 16 深循环窗口（(t-k)%16 动态索引）改成 16 级移位寄存器， 索引退化为固定连线，mux2_2 从 2,239 降到 685（mux 总数 -64.5%），逻辑单元 12,288 → 11,475。 同时加 h_in/h_out 链值接口做多块流式，顶层换成 AXI4-Lite 从接口。

先在 24.0 ns 跑一代做可比对照：面积小 6.6%，三 corner 余量从 +1.25 放大到 +6.44，说明关键路径真的短了。 于是再压到 18.0 ns：三 corner 仍全正（+1.03 / +0.80 / +0.56，hold ≈ +0.40，TNS 0）， 55.56 MHz —— 同一块 0.4096 mm² 的 die、同一个库、同一个时钟端口，比 v6 快 33%。

代价如实记：功耗 6.84 → 9.41 mW（频率 +33%，单位频率功耗基本持平），v7 买到的是更快、更小、能集成，不是更省电。

标准流程：把手伸开，让流程自己跑完

此前所有「时序通过」的版本，都对时序动过手 —— ctsfix 线上每一版都插了手工 delay。这一段说的是另一件事：不插任何手工 holdfix，让 OpenLane 自己从综合走到 GDS，看它能不能自己立住。run 名 stdflow，约束仍是 18 ns。

跑通的顺序：verilator lint（0 error / 0 warning）→ 综合（Yosys，AREA 0，11,475 单元）→ 布图规划 → IO / tap / decap / 电源规划 → 全局布局 → CTS → resizer → 全局布线 → 详细布线 → Magic DRC → 三角 SPEF 提取 → 多角 STA → Magic 出 GDS → spice 提取 → netgen LVS。中间没有一次人工干预。

详细布线是这轮最直观的一段：TritonRoute 的违例数一路收敛 4974 → 4733 → 1076 → 79 → 34 → 1 → 0，末轮打出 No Magic DRC violations after detailed routing。

这一轮撞到的两个坑，都不是设计问题

坑一：locale 把 lint 弄崩了。flow 只跑了 20 秒就退。根因是宿主注入了 LC_ALL=en_US.UTF-8，而 chroot 里没有这个 locale，于是每次 bash 启动都往 stderr 打一行 setlocale: cannot change locale；tcl 的 exec bash -c 把任何非空 stderr 都当命令失败，lint 还没开始就被判死。修法是在 chroot 启动命令开头补 export LC_ALL=C; export LANG=C。

坑二：magic 8.3.483 的 extract 会无限等下去。OpenLane 默认的 extract_spice.tcl 用的是裸 extract，也就是 incremental 模式。碰到 physical-only 子 cell sky130_fd_sc_hd__tapvpwrvgnd_1（这个设计里有 5,496 个实例）时，magic 会沿基路径和全部搜索路径去找 tapvpwrvgnd_1.ext —— PDK 只带 .mag、不带 .ext，找不到之后它没有回退成现场提取，而是进入无限重试。进程状态 S、wchan=request_wait_answer、每秒约 1,000 次 voluntary context switch、几乎不耗 CPU —— 看上去像死锁，其实是找不到文件又不肯放弃。当年 ctsfix3 就死在同一行。

独立实验先排除了「magic 坏了」：对单个 cell 用绝对路径 load 再 extract，正常生成 856 B 的 .ext；但裸 load <cellname> 只会 "Creating new cell"，建一个空的。这说明 magic 本身没坏，坏的是 incremental 的查找策略。修法换成 extract all：显式递归提取 root 加全部 children，magic 按依赖顺序现场生成每个子 cell 的 .ext，完全不依赖预存文件。干净目录一次就跑过，产出 153 个 .ext（顶层 17,151,056 B），随后 ext2spice lvs 出 LVS 网表（3,463,849 B，153 个 subckt）。这个修法脚本随 Release 一起放出去了，因为它跟具体设计无关，任何 sky130A + OpenLane 的 run 都会撞上同一个坑。

边界：这一页不写的东西

不是量产芯片。作品集与方法论验证，商用价值为零 —— SHA-256 加速器本身没有稀缺性。

W/E 边补电源 pad 的账单独算过，结论不塞在这一页。100 个 pad 里 W/E 各 25 个全是 PAD_gpiov2，电源 pad 只有 4 个（N 边一对 3.3V、S 边一对 1.8V）。「50 个 IO 电源悬空」这个说法不成立：它们挂在侧总线上，由 1440 条缝桥分配，缺的是冗余注入点而不是连接。按方数量，环上最远绕行 876 方，环→stripe 接头只有约 7 方；加宽环和加 W 边入口都约是 2 倍改善，前者不要 IO 代价、后者要拿信号换。加宽的天花板已经实测：met4 超 3.0 µm 撞 m4.5ab（3.2 时多 4 条），所以 VPWR 停在 2.9、VGND（met5 无同类规则）可以到 3.2，见 core_power_ring16.txt。更正（chip22 那轮）：「VGND 可以到 3.2」是 chip16 当时的保守取值，不是上限 —— 改掉出线拓扑后 met5 环实测到 12.9 µm 仍对上一版零新增，见上文 chip20→chip22 一节与 core_power_ring22.txt；不动环中心线时真正的天花板是 met5 12.9 / met4 2.9。再更正（chip23/24 那轮）：把 VGND 环中心线内移 2 µm 后，met5 环宽实测到 16.9 µm 仍对 chip22 零新增（17.0 才报 1.550 的 2 条 m5.2）；并且 met4 环外沿那条线只是版图意图余量 —— 跨层面积重叠不构成短路（三版 met4 ∩ met5 重叠多边形都是 1301 个、两网始终分离），见 core_power_ring23.txt。上限的真实卡点是 S/N 出线竖条的位置，不是 met4。第三次更正（chip25 那轮）：把整环外移 20 µm 后，环宽仍是 16.9、间距仍是 1.600 / 0.100，DRC 仍是 22019、对 chip23 零新增 —— 说明外移根本不改变任何间距，只是把 core ↔ 环的通道从 12.05 开到 32.05（闭式里 SHIFT 两边同时出现、直接消掉）。外边界要等环外沿碰到 pad 内边（200）或四角缝桥链，对应 SHIFT ≈ 640–710，那时环已进 pad 区、无工程意义，与内边界 29.05 对称。见 core_power_ring25.txt。取舍与代价清单见 evidence/w_e_power_pad_tradeoff.txt。

v1–v4 时序确实没收敛。SPEF 重签核后 setup 余量全负（v4 nom -7.63 ns），按签核标准不合格。不写这一点，就是把估算当签核。

v5 的通过靠的是降低频率，不是提高设计能力。38.46 MHz 不代表性能强，它是在该工艺下"真能签核"的工作点。

22.75 ns 是"v6 那套 RTL"的边界，不是工艺边界。v7 换掉消息调度后，18 ns 三 corner 仍全正余量（最紧 +0.56 ns）。把架构上限说成工艺上限，是这个项目前六代差点犯的错。

DFT 扫链仍未插入；ECO 已做一轮但没清干净。ECO 版把 Slowest 的 max_slew 从 275 压到 21 条；DRC 从 6 条 li.6 修到 0 条（两套引擎都是 0）；引脚开路已修到 0 个（成因是 36 条网从未布线）。LVS 的变化是：上一轮 ECO 版（327 颗 diode）通过、并已做成一条命令 88 秒复现；本轮 ECO 版（347 颗，+20）同一条命令跑出来是不通过——顶层 .subckt 少了 VGND 一脚，15,981 vs 15,983 器件、15,799 vs 15,828 网，卡点由「提取链复现性」更正为「ext2spice 会读到旧缓存」之后，又落到「顶层丢脚」这一条。仍未闭合的是：那 2 个器件 / 29 条网差额与丢 VGND 是否同源（未定位）、天线从 1 条涨到 16 条、max_fanout 61 条（详见上一节）。（2026-11-11 补正：同版参考下 145 个单元类逐类相等，「2 器件 / 29 条网」已证死为参考不同源的产物；卡点收敛成 GDS 侧电源网并成一条，且与 20 颗二极管无关（无二极管变体同样并）；短接坐标仍未定位。原句保留，不覆盖。）

吞吐仍然很低。约 15 MB/s，比带 SHA-NI 的 CPU 慢两个数量级；多块流式省的是软件搬运，不是算力。padding 仍由软件完成。

DFT 扫链仍未插入；ECO 已做一轮但没清干净。ECO 版把 Slowest 的 max_slew 从 275 压到 60 条；DRC 已从 6 条 li.6 修到 0 条（只补 li1 面积，网表与密度都没动）；LVS 仍未通过、天线是 1 条不是 0 条（详见上一节）。所以「可测、可修」这两环都还没闭合。（这一条是更早一轮的原话，已被上面那段取代：max_slew 现为 21 条、LVS 上一轮 ECO 版（327 颗 diode）已通过且一条命令可复现、天线已是 16 条。原文保留，不覆盖。）
